# 共用归档与 Git 协调规则

本指南给所有协作阅读的 Agent 使用。先检查本文件与仓库最新状态，再编辑。

> **最新用户决定（2026-10-17）见同目录 `decisions.md`，先行阅读**，含归档结构、发布授权与全书视角初版的变更。

## 归档结构

优先沿用现有归档；当前约定的目标结构：

```text
reading-notes/
├── index.html
├── 规范.md                  # 历史版人读规则；本 Skill 为当前操作版
└── books/<book-slug>/
    ├── overview.html         # 开读即建的全书视角初版（含来源标注）
    ├── notes/YYYY-MM-DD.html
    ├── final.html            # 完读后整书汇编
    └── final.epub            # 完读后 EPUB
```

旧文件名（如 `书名-YYYY-MM-DD-总结.html`）可继续使用；不要为了统一而移走、覆写或删除现有公开文件。新旧路径并存时同步更新 `index.html` 中的链接。

已按旧路径发布的书（如《住小房子的女人》《玉簟秋》：`notes/<年份>/<日期>-<slug>.html` + `books/<slug>/index.html`）**保持旧路径继续更新，不迁移**；新书一律按上面的目标结构创建。

## 并发工作规则

0. **实现方式不耦合**：本规则约束协作目标与协议，不约束各 Agent 的实现方式。代码自动化、Agent 直接操作浏览器、人工整理都是被认可的手段；代码类 Agent 的实现细节只在 `automation-code-agent.md`，仅约束其自身。不要假设其他 Agent 的技术栈，不要因实现方式不同而重复或覆盖对方的产出。
1. 修改前检查当前任务中的文件和 GitHub 最新 `main`，确认这本书/日期的拥有者与其他 Agent 正在处理的文件。
2. 同一个文件同一时间只允许一个 Agent 写入。认领文件后只改认领范围；碰到并行改动先暂停并协调。
3. 不用旧的本地快照重建整个站点。发布前比较线上、当前 `main`、本地差异，保留线上较新的内容与其他 Agent 已提交的增量。
4. 每个工作分支只含单项变更，建议 `notes/<book-slug>/<date>-<agent>` 或 `site/<date>-<change>`。先 `git fetch origin`，再从最新基线切分支。
5. 提交前运行 `git diff --check`、检查 `git status` 和 `git diff --stat`。确认无误后推分支并通过 PR 或已批准的合并流程；禁止强推、覆盖式上传、无审查地把分支整体并入 `main`。
   **例外（2026-10-17 用户授权）**：weread-auto 每日自动阅读产出的内容（日期笔记、overview/final、EPUB、索引更新）已获持续授权，可直接提交并合并 `main`，无需分支与 PR；仍需 `git diff --check`、本地校验与发布后在线验证。其他 Agent 的人工改动不适用此例外。
6. Pages 只发布经授权的已核对版本。推送会让文件公开时，必须确认这次批准覆盖了具体文件；过去对一批内容的批准不自动覆盖未来新笔记。
   **例外（同上）**：weread-auto 日产内容的持续授权已覆盖，见 `decisions.md` 第 2、3 条。
7. 合并或发布后核对部署结果，再检查主页、各页面、下载链接、时间标签与手机宽度排版。未在线验证前不能说“已发布”。
8. 任何计划运行失败、被打断、登录失效、发生 Agent 冲突或结果不确定，都要在当前 Cue 对话里及时直接通知用户，说明实际完成情况与下一步；更新 roster/交接板不算通知。

## 文件命名与笔记范围

- 日期笔记：`<book-slug>/notes/YYYY-MM-DD.html`；同一本书一天多次阅读合并到该书当天的同一文件并标注各段，不同书籍即使同日阅读也各自保存一篇。
- 全书视角初版：`<book-slug>/overview.html`。开读即建，基于官方简介/目录、公开划线点评与模型自身知识给出完整全书视角（主旨、结构、关键观点、主题关系）；四层来源标签分明，未经亲读确认的部分保持推断标记——它不是最终总结，也不是一张空地图。
- 完读汇编：只有整本实际读完并校订后才更新 `<book-slug>/final.html` 和 `.epub`。
- 每次短读只新增/更新当天笔记；不要每天重做全书汇编。确有重要理解变化时，在 `overview.html` 注明依据并更新。
- 标签建议：`亲读`、`官方简介/目录`、`用户材料`、`公开评论/划线`、`综合推断`。不得混写来源。
- 开始、交接、完成或受阻时，按 `agent-communication.md` 更新自己的协作记录；不要覆盖别的 Agent 的条目。`agent-roster.json` 是 Agent 类型、时段、当前书目、完读状态与运行状态的唯一登记源。公开协作文件只记录必要元数据，不放凭据、私人聊天内容或未获公开授权的读书笔记。
- 接入新平台时，新增独立的 `references/platforms/<platform>.md`，从 `platform-adapter-template.md` 起步；把实际验证与待验证事项分开，不将平台特有步骤混入共用流程。

## GitHub 身份验证

- 优先走已批准的 GitHub CLI/OAuth 或 Git Credential Manager 浏览器授权；GitHub 官方支持 HTTPS Git 凭据助手。
- 一次性设置的常见方式：`gh auth login --hostname github.com --git-protocol https --web`，完成浏览器授权后执行 `gh auth setup-git`。检查 `gh auth status`；后续对已授权仓库进行 `git push` 通常复用凭据，不应每次重新输入令牌。
- 如果授权状态丢失、过期、缺少仓库权限或组织重新要求批准，按真实提示处理；不要声称一次性授权永久有效。
- 不要求用户把 PAT、密码、验证码贴进聊天。禁止把凭据写在 remote URL、脚本、仓库文件、提交信息或 shell 日志中；不要用明文长期保存令牌。
- 该电脑由多个 Agent 共用。GitHub 凭据属于账户敏感凭据，只能由拥有授权的用户/Agent 的既定凭据助手使用；不可复制给其他系统或绕过账号权限。Agent 可以共享仓库规范，不意味着每个 Agent 都获得额外 GitHub 权限。

## 发布边界

公开站点可能被任何人访问。公开笔记、预读框架或 EPUB 只限用户明确批准的那批内容；新增内容默认只留在私有归档。即使拥有 `git push` 权限，也不得把未获授权的文件发布到 Pages。

持续授权（2026-10-17）：weread-auto 每日自动阅读产出的内容已获用户授权直接发布并自动合并 `main`（理由：无人值守场景无法每次人工确认）。该授权**不覆盖**其他来源的文件——人工创作、其他 agent 的改动仍按上面的逐次授权执行。

## 2026-10-18 补充：书目独占、场次续读与跨书综合

所有类型的阅读 Agent 必须先按 `reading-state-protocol.md` 核对最新 `book-registry.json`，独占认领被权威 main 接受后才开始阅读；共享状态用 revision 和非强制推送串行更新，冲突重新检查，不盲目重放。roster 的本人登记与他人记录边界不变。每场结束私下保存确认续读点和一个承接问题；同书同日合并但逐场保留记录。每累计 3 本唯一已确认完读书生成不重叠的私有综合批次，重复场次/重读不重复计数。

私有场次记录、承接问题和跨书综合正文保存在仓库外，不进入公开 Git、Pages、索引或 weread-auto 的日产发布授权。模板中的 `data-visibility="private"` 只是标识，不是安全控制；任何公开导出必须删除整个私有区段，禁止仅用 CSS 隐藏。没有经过该处理的私有日期笔记不得放入仓库。

本次用户明确批准这三项共享规则直接推进当前默认分支 `main`（不创建 `master`），仅覆盖本次规则、模板、最少共享元数据和校验工具；不扩展任何私有阅读内容的发布授权，也不授权改其他 Agent 的个人记录或代码内部实现。
