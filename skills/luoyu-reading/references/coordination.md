# 共用归档与 Git 协调规则

本指南给所有协作阅读的 Agent 使用。先检查本文件与仓库最新状态，再编辑。

> **先读同目录 [decisions.md](decisions.md) 顶部最新用户决定（2026-10-22）**：按环境／书目分锁与当前错峰安排取代旧全局锁及旧排班；协调者职责取代“管理员只读、不派活”限制；历史决定保留原文，不作为当前排班指令。

## 协调者职责与权限边界（2026-10-20）

- 由管理员／协调者负责整体错峰排班、阅读任务分发与共享归档页面设计，不读正文。按 Asia/Shanghai 每日 02:00–06:00 禁读；浏览器按整点／半点错峰，Windows 独立本地 PDF 自主管理、不同书且资源独立时可并行；实际窗口、不补跑及请假／暂停边界统一见 [最新决定](decisions.md)，不在此复制排班表。
- 在已授权队列及既有归属内提出任务与交接；书目归属、认领、活动场次与续读点仍以 `book-registry.json` 为准，不能用派活覆盖独占认领或借排班转移书目。实际排班由各 Agent 自己维护其 roster 镜像，协调者核对但不代写。
- 严禁改其他 Agent 的个人记录、续读点、个人排班镜像或阅读历史；不修改其专属实现，不替其开始、结束、恢复或登记阅读。只根据实际事件报告，计划场次和约20分钟目标都不等于实际完成。
- 做文章呈现、共享归档页面或组件前，先读 [archive-ui.md](archive-ui.md)，它是唯一 UI 规范入口。同类区块复用一致规范，不另起副本；共享设计仍须认领文件、保留他人增量并经差异审查，不借样式统一重写他人正文、事实或历史笔记。该职责不扩展公开发布授权。
- 本次规则更新仅限 `SKILL.md`、本文件、`agent-communication.md`、`decisions.md`；独立规则分支开 PR、差异审查后才合并，不复用 UI／角色名单任务分支，不改 roster、registry、当天事件日志、历史笔记或 `agent-room/*` 页面。规则合并不代表各 Agent 的实际调度、镜像或已安装 Skill 已同步。

## 归档结构

优先沿用现有归档；当前约定的目标结构：

```text
reading-notes/
├── index.html
├── 规范.md                  # 历史版人读规则；本 Skill 为当前操作版
└── books/<book-slug>/
    ├── overview.html         # 开读即建的全书视角初版（含来源标注）
    ├── notes/YYYY-MM-DD.html
    ├── final.html            # 完读后整书汇编
    └── final.epub            # 完读后 EPUB
```

旧文件名（如 `书名-YYYY-MM-DD-总结.html`）可继续使用；不要为了统一而移走、覆写或删除现有公开文件。新旧路径并存时同步更新 `index.html` 中的链接。

已按旧路径发布的书（如《住小房子的女人》《玉簟秋》：`notes/<年份>/<日期>-<slug>.html` + `books/<slug>/index.html`）**保持旧路径继续更新，不迁移**；新书一律按上面的目标结构创建。

## 阅读并发与状态写入

阅读按 [状态协议](reading-state-protocol.md) 的 `active_sessions` 核书目、环境与资源；同书或共享浏览器互斥，独立本地 PDF 与不同书的浏览器阅读可并行。共享 JSON／沟通文件的 Git 写入仍全局串行，不能整表覆盖其他场次。保留旧 `active_session` 供原 owner 收尾，不迁移当前锁；旧写入端未确认接入前不启用并行。Windows 本地阅读自主管理，不新增管理员逐场转达门槛、不代改其实现或排班。

## 并发工作规则

0. **实现方式不耦合**：本规则约束协作目标与协议，不约束各 Agent 的实现方式。代码自动化、Agent 直接操作浏览器、人工整理都是被认可的手段；代码类 Agent 的实现细节只在 `automation-code-agent.md`，仅约束其自身。不要假设其他 Agent 的技术栈，不要因实现方式不同而重复或覆盖对方的产出。
1. 修改前检查当前任务中的文件和 GitHub 最新 `main`，确认这本书/日期的拥有者与其他 Agent 正在处理的文件。
2. 同一个文件同一时间只允许一个 Agent 写入。认领文件后只改认领范围；碰到并行改动先暂停并协调。
3. 不用旧的本地快照重建整个站点。发布前比较线上、当前 `main`、本地差异，保留线上较新的内容与其他 Agent 已提交的增量。
4. 每个工作分支只含单项变更，建议 `notes/<book-slug>/<date>-<agent>` 或 `site/<date>-<change>`。先 `git fetch origin`，再从最新基线切分支。
5. 提交前运行 `git diff --check`、检查 `git status` 和 `git diff --stat`。确认无误后推分支并通过 PR 或已批准的合并流程；禁止强推、覆盖式上传、无审查地把分支整体并入 `main`。
   **例外（2026-10-17 用户授权）**：weread-auto 每日自动阅读产出的内容（日期笔记、overview/final、EPUB、索引更新）已获持续授权，可直接提交并合并 `main`，无需分支与 PR；仍需 `git diff --check`、本地校验与发布后在线验证。2026-10-18 用户进一步批准：此类面向用户的微信读书阅读笔记（含浏览器/手动来源）及必要索引维护也可按已批准流程直接推进 `main`，不再逐篇询问；其他不在范围内的人工改动仍遵循分支与审查规则。
6. Pages 只发布经授权的已核对版本。推送会让文件公开时，必须确认这次批准覆盖了具体文件；无持续授权的内容不得仅凭过去某批批准自动公开；此类面向用户的微信读书阅读笔记已有 2026-10-18 持续公开授权。
   **例外（同上）**：weread-auto 日产内容的持续授权已覆盖，见 `decisions.md` 第 2、3 条。
7. 合并或发布后核对部署结果，再检查主页、各页面、下载链接、时间标签与手机宽度排版。未在线验证前不能说“已发布”。
8. 任何计划运行失败、被打断、登录失效、发生 Agent 冲突或结果不确定，都要在当前 Cue 对话里及时直接通知用户，说明实际完成情况与下一步；更新 roster/交接板不算通知。

## 文件命名与笔记范围

- 日期笔记：`<book-slug>/notes/YYYY-MM-DD.html`；同一本书一天多次阅读合并到该书当天的同一文件并标注各段，不同书籍即使同日阅读也各自保存一篇。
- 全书视角初版：`<book-slug>/overview.html`。开读即建，基于官方简介/目录、公开划线点评与模型自身知识给出完整全书视角（主旨、结构、关键观点、主题关系）；四层来源标签分明，未经亲读确认的部分保持推断标记——它不是最终总结，也不是一张空地图。
- 完读汇编：达到用户授权的亲读完读或AI阅读完读条件后，才更新 `<book-slug>/final.html` 和 `.epub`；AI路径须标明「AI阅读」及笔记来源，不能把AI导览写成亲读范围。
- 每次短读只新增/更新当天笔记；不要每天重做全书汇编。确有重要理解变化时，在 `overview.html` 注明依据并更新。
- 标签建议：`亲读`、`官方简介/目录`、`用户材料`、`公开评论/划线`、`综合推断`。不得混写来源。
- 沟通记录先读 [紧凑索引](agent-communication.md) 与 Asia/Shanghai 今天的 `agent-communication/YYYY/MM/YYYY-MM-DD.md`，仅按需追溯相关旧日。开始、交接、完成或受阻时，按事件实际发生日追加对应日文件，不再向索引追加事件；新日期维护当月目录，跨日、补记与并发更新遵守索引规则。不要覆盖别的 Agent 的条目。`agent-roster.json` 只登记 Agent 身份、类型、排班及个人状态镜像；书目归属/认领与完读以 `book-registry.json` 为权威来源。公开协作文件只记录必要元数据，不放凭据、私人聊天内容或未获公开授权的读书笔记。
- 接入新平台时，新增独立的 `references/platforms/<platform>.md`，从 `platform-adapter-template.md` 起步；把实际验证与待验证事项分开，不将平台特有步骤混入共用流程。

## GitHub 身份验证

- 优先走已批准的 GitHub CLI/OAuth 或 Git Credential Manager 浏览器授权；GitHub 官方支持 HTTPS Git 凭据助手。
- 一次性设置的常见方式：`gh auth login --hostname github.com --git-protocol https --web`，完成浏览器授权后执行 `gh auth setup-git`。检查 `gh auth status`；后续对已授权仓库进行 `git push` 通常复用凭据，不应每次重新输入令牌。
- 如果授权状态丢失、过期、缺少仓库权限或组织重新要求批准，按真实提示处理；不要声称一次性授权永久有效。
- 不要求用户把 PAT、密码、验证码贴进聊天。禁止把凭据写在 remote URL、脚本、仓库文件、提交信息或 shell 日志中；不要用明文长期保存令牌。
- 该电脑由多个 Agent 共用。GitHub 凭据属于账户敏感凭据，只能由拥有授权的用户/Agent 的既定凭据助手使用；不可复制给其他系统或绕过账号权限。Agent 可以共享仓库规范，不意味着每个 Agent 都获得额外 GitHub 权限。

## 执行环境与 GitHub 写入授权（2026-10-22）

- 每次写入前，在实际执行写入的环境核对授权通道与目标仓库权限。Agent 主会话、协调者会话、独立浏览器子任务及 GitHub Connector/API 可能使用不同身份或权限；一个环境的 `gh auth status`、仓库 `permissions` 或既往成功推送，不能证明另一个环境可写。GitHub CLI/OAuth 与 Connector 不是同一授权。
- 连接器已绑定或只读访问成功，不代表创建 blob、提交或推送具备权限。记录失败的实际步骤、端点及原始错误；遇 403、权限检查失败或授权等待时停止受阻写入，不换用其他 Agent 的凭据、不把凭据传入子任务、不盲目重试。
- 排班阅读前尽可能在窗口外完成必要的授权和写入通道预检；不要让连接／权限确认等待占满阅读窗口。窗口开始时仍未就绪，或窗口内发生阻塞，应立即向用户报告实际卡点和下一步；未登记成功前不打开正文；浏览器场次还须收到本场“已转达”，此门槛不泛化到 Windows 独立本地 PDF，错过的场次不补跑。
- 若浏览器子任务负责阅读而不具备 Git 写权限，且其责任 Agent 的主会话具备自己的获批写入通道，可采用无凭据两段式：责任 Agent 主会话核验最新 main、串行登记活动锁并等待管理员转达；浏览器子任务只做获授权的网页阅读／AI问答并回传内容补丁；责任 Agent 主会话再检查、提交阅读产出与收尾。不得将 CLI 登录、令牌或其他凭据传给子任务或其他 Agent；若安全交接不可行，就停在正文前并报告。

## 发布边界

公开站点可能被任何人访问。用户已于 2026-10-18 明确批准此类面向用户的微信读书阅读笔记今后默认公开，无需逐篇再次询问；本次完整笔记按此授权发布。其他内容仅按各自明确授权范围发布，不能把 `git push` 权限视为任意文件公开许可。

持续授权（2026-10-17）：weread-auto 每日自动阅读产出的内容已获用户授权直接发布并自动合并 `main`（理由：无人值守场景无法每次人工确认）。2026-10-18 补充授权将此类面向用户的微信读书阅读笔记纳入持续公开范围，不限代码、浏览器或手动来源；不覆盖跨书综合、内部协调和原始运行记录，也不授权改动他人个人记录或代码 Agent 内部实现。

## 2026-10-18 补充：书目独占、场次续读与跨书综合

所有类型的阅读 Agent 必须先按 `reading-state-protocol.md` 核对最新 `book-registry.json`，独占认领被权威 main 接受后才开始阅读；共享状态用 revision 和非强制推送串行更新，冲突重新检查，不盲目重放。roster 仅登记身份、类型、排班与个人状态镜像，不能作为书目归属/认领或完读的权威来源；本人登记与不得改他人记录的边界不变。每场结束私下保存确认续读点和一个承接问题；同书同日合并但逐场保留记录。每累计 3 本唯一已确认完读书生成不重叠的私有综合批次，重复场次/重读不重复计数。

原始私有场次记录、内部协调、session-close/active-run 元数据及跨书综合正文与其私有问题保存在仓库外，不进入公开 Git、Pages 或索引。面向用户的此类微信读书阅读笔记按 2026-10-18 持续授权公开，其中作为读书内容展示的续读点和反思问题不等于原始内部记录；跨书综合隐私规则不变。模板中的 `data-visibility="private"` 只是标识，不是安全控制；任何公开导出必须删除整个私有区段，禁止仅用 CSS 隐藏。没有经过该处理的私有日期笔记不得放入仓库。

本次用户明确批准这三项共享规则直接推进当前默认分支 `main`（不创建 `master`），仅覆盖本次规则、模板、最少共享元数据和校验工具；不扩展任何私有阅读内容的发布授权，也不授权改其他 Agent 的个人记录或代码内部实现。
