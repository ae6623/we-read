# 两个 Cue 账号的团队协作

本规则用于两支团队同时协作，而不只是旧账号停用后的迁移。两队共用同一权威仓库最新 `main` 与同一本 `book-registry.json`；账号、角色显示名或本地工作区均不能产生第二套书目事实。

## 对外用别名，对内用真实 UID

- 为每支团队约定唯一、公开且稳定的团队别名；成员对外用 `团队别名/角色别名` 标识。显示名可以相同，也可以改变，不作责任或冲突判定依据。角色别名可沿用既有逻辑角色键，但完整组合必须区分两队。
- canonical Agent UID 仅在所属 Cue 账号内部使用。各队在自己的私有配置中维护“团队别名/角色别名 → 本账号 canonical Agent UID”的映射、工作区及实际配置回执；不把 UID、账号标识、私有路径或配置快照写入公开仓库，不拿另一账号的 UID 发消息或绑定任务。
- 团队别名尚未约定、旧角色键无法唯一对应团队或责任不清时，标待确认并停止冲突写入；不得把同名当同一 Agent，也不得用新别名冒领旧 owner。

## 共用一份事实，保留既有锁

书目归属、claim、活动项、续读点与完读计数只认同一最新 `main` 上的 registry，始终单书单 owner。两队按稳定 `book_id` 去重，按 `book_id`、`environment_id`、`resource_ids` 核冲突，具体字段与旧锁兼容依 [状态协议](reading-state-protocol.md)。不同账号不自动等于独立环境；实际共用浏览器或设备资源必须使用相同资源别名，不靠团队前缀改名绕锁。

新公开协作记录须写明团队别名及角色别名，并引用现有权威 `agent_id`／owner 键以便对照。现有 registry、roster、owner、活动锁与历史身份字段不因本规则批量改名；新增或调整机器可读身份键之前，须先明确无歧义的团队归属、原责任人的安全交接及各写入端兼容，再按另行获准的变更执行。本规则不引入字段迁移，不允许在 schema 未接入前自行添加替代 owner 或 UID。

管理员以稳定团队别名＋角色别名核责任，而不是显示名；同一 run_id 交叉核对 registry、实际日期事件及 `reading-state:` 提交。只有不同书、不同环境且资源无交集，并满足现有写入端接入门槛，才可按协议并行。旧 `active_session` 非空仍全局独占；不超时抢锁，不代释放，不因换账号重建角色而继承授权、owner 或本场放行。

## 工作区分开，Git 写入串行

各队自行维护自己的工作区、分支、内部 UID 映射、应用权限与实际调度，不共用未提交工作树，不复制他队凭据。每次写入都重新核对远端最新 `main`、revision、身份归属及资源锁；仅提交自己获授权的增量，保留另一团队改动。共享 JSON、沟通记录、索引和交接文件的 Git 写入仍全局串行；分支提交不算登记成功，必须进入权威 `main`。非快进、revision 变化或责任冲突时重新取最新状态并核查，不盲目重放、不整表覆盖、不强推。

本规则不新增排班、跨账号通知通道或管理员逐场放行要求，不改变浏览器既有转达门槛与 Windows 独立本地 PDF 自主管理边界，也不启动或恢复阅读。

## 公开交接只留必要摘要

`team-handoffs/` 仅保留获准的“今日进展／明日规划”及必要团队／角色别名、书目 ID、准确状态、阻塞、下一安全动作与公开证据链接。计划、已登记、已开始、已完成、已发布、在线核验与已通知分开写；未知就写未知。日报是快照，不替代最新 registry，也不是另一队接管指令。

不得放私人聊天、原始 AI 答复、原始场次或私有分析稿、凭据、canonical Agent UID、私人路径；不得通过转述泄露这些内容。必要私下交接另经已授权的私下通道，公开摘要不扩大既有公开授权。规则入库、日报入库、团队实际安装／同步及通知送达是不同事件，分别留证。
