# 共享书目、续读点与三本综合

适用于浏览器、代码和人工阅读 Agent；只规定协作结果，不规定阅读实现。每场开读前必须阅读本文件、最新 `book-registry.json`、`agent-roster.json`、[沟通索引](agent-communication.md) 与 Asia/Shanghai 今天的 `agent-communication/YYYY/MM/YYYY-MM-DD.md`；仅在跨日续接、未解决交接或追溯证据时再读相关旧日，不通读全部历史。交接事件按实际发生日期追加日文件，不追加索引。不得改其他 Agent 的个人记录或代码实现。

两个 Cue 账号同时协作时，先按 [双团队协作规则](cross-team-coordination.md) 核清团队别名／角色别名与现有 owner 键的对应；canonical Agent UID 只留各自账号内部。单书单 owner、同一 registry、资源冲突及 main 接受门槛不因跨账号而放宽；本次不迁移现有身份字段或活动锁。

## 两类共享状态各司其职

- `agent-roster.json` 仅作为身份、类型、排班及个人状态镜像的登记源，保持原字段兼容；其中个人当前书/完读字段不得覆盖或裁定 `book-registry.json` 的权威书目状态。仅本人更新本人条目。
- `book-registry.json` 是按书去重的队列、独占责任归属、下一续读点与跨书批次的唯一共享登记源。每书一个稳定 `book_id`，同一本书的别名、重复加入书架或换 Agent 不得另建计数。优先核对平台 ID；未知就留空，以书名+作者人工核对，版本/译本不明先标待确认。
- 不因旧页面存在 final/EPUB 就推断完读。首次迁移只导入 roster 明确确认的完读书；本段中的迁移数量仅是历史基线，当前唯一完读数以 registry 的 `synthesis.unique_completed_count` 为准。迁移不冒充新阅读，也不编历史认领时间或下次问题。
- 两处状态矛盾、远端不可访问或活动状态不明时，停止新开读并直接在 Cue 私聊说明；不自行覆盖或改写他人状态。

## 认领和选书

**先执行黑名单门槛，再按下列优先级排序。** 每次读取最新 main 的 [唯一黑名单](reading-blacklist.json) 及 [过滤规则](reading-blacklist.md)。管理员推荐、选书排班／派活，所有阅读员挑选、认领、默认续读与开读均适用；命中具体书或职业等已禁主题直接跳过，选择已授权队列中下一本合格书，不逐次询问。主题不明由选书 Agent 查非正文元数据，仍不明暂不选，不自动加入永久名单。用户指定或旧未完认领不自动解禁；不借黑名单改 owner／claim、抢锁、清锁或重写历史。通过黑名单不等于可恢复 paused／blocked 书。规则缺失或无效先停止新选书并报告，不默默放行；具体书与主题规则只以用户明确决定持久维护，单次跳过不算永久禁读。只读工具与返回码见规则说明。

1. 用户指定书目优先；但**不能越过别人持有的认领**。若指定书已被另一 Agent 认领，先交接或由原责任 Agent 继续，不并行读。已完读书只有用户明确要求重读才允许打开。
2. 未指定时续读本人尚未完成且认领仍有效的书；之后按用户书架最近添加顺序选未完读、未被认领书。最近添加时间不明则先核对，不自造队列。
3. 新书入队为 `queued`，owner 为空、claim.state 为 `unclaimed`。认领成功后设 owner 为本人、claim.state 为 `held`、status 为 `in_progress`，记录实际认领时间和依据。切换书目时，旧的未完书保持本人责任（可标 `paused`），除非本人明确释放或交接；不得默默丢弃。受阻用 `blocked`，默认仍保留责任，不能靠超时抢占。
4. 认领是书籍跨场次责任，不是每场用完就释放的临时锁。每场结束清除自己的活动场次，但未完书继续保留 owner。满足用户授权的完读路径后设 `completed`、释放 owner，并保留 completion.confirmed_by 与证据。完读路径可以是有证据的亲读完读，也可以是按 [AI章节问答规范](ai-ask-book.md) 完成规定章节笔记与「读后思考」的AI阅读完读；后者须在证据中明确标AI来源，不得写成亲读。转交须旧 owner 明确释放且确认无运行，新 owner 再认领，交接板追加事件，不能改旧 owner 的个人记录。重读沿用同一 book_id、保留 completion，不增加唯一计数。

## 并发：成功落盘不等于跨机认领成功

`revision` 每次修改加 1。对共享状态使用同一个串行写入流程：

1. 获取最新远端 main，核对基线 revision、owner、roster 与交接记录；同机写入也须串行，不同 Agent 不得同时写同一文件。
2. 只在最新基线上提交本人合法变更，用普通非强制推送或已有受审查的合并通道接受到 main。**只有变更进入权威 main 后，才算认领/活动场次成功，才可翻页**。PR 分支里的拟认领不生效。
3. 非快进拒绝、冲突或 revision 已变化时，重新读取最新 main，重新做资格与活动检查；不能盲目 rebase/合并 JSON 后重推，更不能强推。任何时刻无法确认唯一 owner 就不开始。
4. 按下节核对全部活动场次，只在**书目、环境和实际共用资源均无冲突**时登记本场。不同书、不同环境且无共用资源可以并行阅读；同一书目跨环境、同一环境或同一共享浏览器仍互斥。全局串行的是共享文件写入，不是所有阅读。核对所有 roster 的运行镜像，但独立环境中有匹配锁的 running Agent 本身不是冲突。
5. 同一 run_id 只有一次开始与一次结束的有效记录；重试更新原场次，不另加完成事件。只有本场 owner 能按 run_id 清除自己的活动项，必须原样保留其他场次；崩溃后的残留锁须先核实任务已停止，记录恢复依据，不以超时自动解锁。

采用此流程不要求浏览器 Agent 写阅读脚本，也不授权改造代码 Agent 的内部实现。无法访问主状态时应报告并交接，不宣称机制已经被另一运行环境接入。

## 按环境／书目分锁（2026-10-22）

### 新活动项与冲突判定

新格式是在 registry 顶层增加可选数组 `active_sessions`，缺失等价于空数组；显式 null 或其他类型非法。每个活动项保留原五个字段并增加三个字段：

```json
{
  "run_id": "<唯一场次标识>",
  "agent_id": "<本场责任 Agent>",
  "book_id": "<稳定且跨平台去重的书目 ID>",
  "slot": "<本人获授权窗口或任务标识>",
  "started_at": "<实际登记时间，带时区>",
  "environment_id": "<稳定、非私密的阅读环境键>",
  "reading_mode": "weread_browser",
  "resource_ids": ["browser:weread-shared"]
}
```

以上仅为空占位示例，不是当前场次或可直接提交的认领。所有标量字段须为非空字符串；`reading_mode` 仅可取 `weread_browser`、`local_pdf`、`other`，`resource_ids` 为非空、无重复的非空字符串数组。

- `environment_id` 表示实际独占的阅读执行环境，不是 Agent 名、书名、run_id 或随场次变化的随机值。共用环境必须用同一稳定键；不得换名绕锁。环境和资源键只用协作别名，不写设备私有标识、路径、登录信息或凭据。
- `resource_ids` 列出实际会操作的所有阅读资源；即使环境键不同，共用浏览器仍须列相同资源键。`weread_browser` 表示阅读方式，**不等于全队共用一个浏览器**。当前确认的资源分组如下：
  - 轻游记 `cue-qingyouji-reader` 与AI读书 `wechat-reading-browser` 共用 `browser:weread-shared`，二者场次（含书内 AI 问答）不得重叠，沿用既有整点／半点错峰。
  - 读书时长专员使用独立浏览器 profile／resource，资源键为 `browser:weread-duration`；不得因其不同书、独立环境的活动项，阻塞上述共享浏览器，反之亦然。独立 profile 必须真实存在，不得只改登记键而继续操作共享浏览器。
  - Windows 读书员主要在自己的云端环境用本地 PDF 等工具阅读，几乎不使用浏览器；不默认登记任一浏览器资源，也不因独立浏览器有场次而受阻。
- 每个 `weread_browser` 活动项须且仅须包含上述一个已确认浏览器键，可同时列出实际使用的其他非浏览器资源；校验器拒绝缺失、未知 `browser:*` 或同时包含两个浏览器键的场次。上述两位共享阅读员须用 shared，不能登记 duration 分流。其他浏览器／环境对应关系尚未确认时，先协调更新规范，不自造别名；资源键只表示互斥范围，不自动创建 profile、不证明登录态或运行端配置已隔离。
- Windows 独立本地 PDF 使用 `local_pdf`，登记自己的稳定环境键与本地阅读器资源别名，不带任何 `browser:*`；不同书且环境、资源独立时可与两类浏览器场次并行。`local_pdf` 不得用于 registry 平台为 `weread` 的书目，也不得伪装实际浏览器操作。若偶尔需要浏览器，须先核实实际 profile／环境、按获授权的相应模式登记全部资源，不默认借用共享浏览器。`other` 不豁免实际资源登记；registry 平台为 `weread` 的新活动项须用 `weread_browser`，其他执行方式另行确认规范，不用模式改名绕锁。
- **环境锁仍按真实执行边界登记**：独立 profile 若仍共用同一独占执行环境，`environment_id` 不能虚构为不同值；只有不同书、不同实际环境且资源不相交时才可并行。独立资源不构成新排班或开读授权；旧格式写入端的接入检查仍适用。未来登记依本规范核清实际资源，不以旧 roster 的实现描述推定仍共用，也不由管理员回改他人镜像或历史日志。
- 全数组中 `run_id`、`agent_id`、`book_id`、`environment_id` 分别唯一；任意两项 `resource_ids` 不得相交。每项 Agent 必须为该书有效 owner，书目必须 held 且 in_progress。同一书跨平台别名仍沿用唯一 book_id，不靠另建条目绕过书目锁。
- 开始写入、owner／claim、资源全集及 revision 必须基于最新 main 同一次核对；收尾仅移除自己的项，并更新自己书目与本人镜像。两个独立场次同时收尾仍按 Git 串行接受，不能用旧快照覆盖另一项。

### 旧锁兼容与安全接入

旧字段 `active_session` 保留：缺失／null 表示无旧锁；非空时仍按原五字段校验并视为**范围未明确的全局独占锁**，不得与任何新活动项并存。不推断旧场次属于哪个环境，不把旧锁复制到新数组，不在规则修订中清除、迁移或改写当前锁。原责任人确认实际结束后依旧协议收尾；之后各责任 Agent 才可按新格式登记未来场次。

所有参与共享写入的责任 Agent 须先确认已读取本协议、支持新数组并保留他人活动项；只检查 `active_session == null` 的旧写入端尚未接入时，**不得启用并行或再用旧格式开新场**。无法确认接入就报告阻塞，由责任人自行适配，不由管理员改造其实现。兼容旧锁只是为安全收尾，不是允许旧／新写入端盲目混跑。格式是可选增量，不要求本次改 registry 的 schema_version 或 revision。

Windows 本地阅读由其责任 Agent 自主管理；不为它新增固定排班、ScheduleTask、管理员逐场“已转达”门槛，也不把浏览器错峰窗口泛化到本地 PDF。共享禁读时间、书目认领、阅读授权、通知与事件留证仍适用；浏览器场次继续按最新决定错峰、遵守已有逐场转达要求，不补跑。本次规则不启动任何阅读、不恢复暂停任务、不更改 roster、registry 或历史记录；入库不代表各执行端已同步或并行已启用。

## 事件通道：按 main 上的新提交判定，不靠索引

读书管理员于 2026-10-19 确认的核对口径，所有 Agent 照此执行：

- **监听对象是 main 上的新提交**。协调方只认已进入权威 main 的提交；分支上的拟提交、本地未推送的 commit、控制台/托盘/日志输出都不构成事件。自查场次是否被看到，用 `git log` 查 main 上的提交，不要靠轮询索引文件或 roster 推断。
- **开始与结束都用 `reading-state:` 前缀的提交标记，并携带同一个 `run_id`**，例如 `reading-state: <agent_id> 认领并开始《书名》（<run_id>）`、`reading-state: <agent_id> 场次收尾《书名》（<run_id>）`。同一 `run_id` 只有一次开始、一次结束；重试更新原场次，不另发事件。缺 `reading-state:` 前缀或缺 `run_id` 的提交不计入场次事件。
- **核对以 `book-registry.json` 与当天日文件为准**：`active_sessions` 全集与兼容旧锁 `active_session`、`resume_point`、`next_question_status` 查 registry，按同一 run_id 交叉核对环境／资源与 owner；新开始事件留必要环境／模式／资源别名，不放私有路径；实际起止时间、实读范围与状态查 `agent-communication/YYYY/MM/YYYY-MM-DD.md` 的当日条目；roster 的 `run_status` 只表示登记状态，不单独作为"正在阅读"的证据。两处不一致时停下核对，不自行裁定其中一处为准。
- **索引只用于定位，不追加事件**。`agent-communication.md` 保留为入口与索引，不写开始/结束/交接/完成条目；事件一律追加当日日文件。
- **失败、受阻或结果不确定必须在 Cue 私聊直报**。Git 记录、提交成功、监听命中都不等于已通知；无发送能力时标「待通知」并交接，不虚填「已通知」。

## 每场结束：精确续读点 + 一个带走的问题

使用 `templates/session-close.json` 的字段，在**私有归档**按 run_id 保存每场结束记录；同书同日仍在一篇日期笔记中追加场次区段，不同书各一篇。`date-note.html` 提供对应占位符。不要把私有正文、问题、摘录或私有绝对路径复制到公开 registry/交接板。

- 写实际起止时间、本场确认范围、状态和唯一 run_id；被打断也要记录真实停止处。无实读的失败不伪造阅读范围。
- `resume_point` 以真实章节/帖子/小节标题及其内部位置为主，分开写平台明确页码（无则 null）、证据来源与实际确认时间。页码字段仅作内部恢复辅助并保留兼容，不要求为凑字段查找页码，不作为面向用户的导航或醒目指标；章节/标题无依据时标待确认，不编造。描述的是**下次从哪继续**，不是仅写“今天读过哪些章节”。平台百分比可单列，但不能换算页码。精确到章节开篇也是有效章节位置，不强求不存在的页码。
- 本场无法确认精确停止点时记录 `needs-confirmation`，保留之前已确认位置及其来源，另标本场位置待核对；不能将旧位置冒充本场新确认。下一场先到平台核实并定位，不盲目翻页或编进度。
- 恰好保留**一个**下一场承接问题，基于已读内容，写清它关联哪个已读观点/场次；尚无可靠依据就标 `needs-confirmation`，下一场核对后再补，不编问题假装读过。本次只配置机制，不补造两本在读书的历史提问。
- 更新 registry 的最少元数据：resume_point、next_question_status（仅状态，不写问题正文）及本人活动项（新格式 active_sessions；旧场收尾才用 active_session），不得清空其他场次；本人更新 roster 与交接记录，并在 Cue 私聊直接发送结束通知。每场开始也直接通知，失败及时直报；文件/控制台/托盘不是 Cue 私聊的替代品。

后续新阅读的用户可见日期笔记、overview/final 与结束消息，按 [共享 Skill](../SKILL.md) 的章节/标题口径组织真实范围，不用页码/页数导航；旧书、已发布笔记、既往记录与历史页码不回改。此口径不迁移字段、不重写 registry 或 session-close 历史值，也不改变实际时长、完成确认及隐私边界。

## 每三本唯一完读：私有跨书综合

1. 完读须有用户授权路径的真实完成证据，不能以“本场完成”、只有文件存在或不可靠 finished 标志代替。AI阅读完读须完成适用篇幅流程规定的章节导览／问答及「读后思考」，并在 completion evidence 中明确标为AI章节笔记完成；它不证明亲读、亲读覆盖或平台时长。按稳定 book_id 首次完读写入不可变 completion 事件，sequence 为下一个整数。同书多 Agent、多个场次、重复通知与重读都只计一次。
2. 每次新完读后，在同一共享状态变更中重算 `unique_completed_count`；每满 3 本生成一个固定批次，不滚动重叠。批次记录 `{batch_id, book_ids, status: pending, owner_agent_id, visibility: private}`。达到阈值即由确认本批最后一本的 Agent 认领该批次；缺少资料则标 blocked，之后重试同一批次，不漏掉或重复创建。
3. 唯一计数包括迁移中已有的已确认完读书及符合本协议的AI阅读完读；当前数量与批次阈值以 registry 为准，不在协议静态文本中硬编码易过期计数。每次结束和开读前都检查 pending/blocked 批次，防止中断漏办。
4. 综合写入仓库外权限受控的私有归档，使用 `templates/cross-book-synthesis.md`：共同观点、真正的分歧/矛盾及适用边界、互补关系、3–5 个回忆问题。每个判断关联书目及亲读笔记、AI章节笔记或其他实际依据，并标明来源类型；不能把AI材料写成亲读证据。找不到真实矛盾就说明，不硬凑。不为写综合重开已完书。
5. 缺少其他 Agent 的私有笔记访问权时，请其提供获授权的私下摘要或报告待补，不改其记录、不公开请求正文。生成后校对三本 ID、来源边界和文件完整性，再把批次状态置 completed。共享状态只留批次 ID/书目/状态/责任人，不写综合正文、私有路径或公开链接。
6. 私有内容**不进入 Git、Pages、站点索引或 weread-auto 的自动发布范围**；现有日产笔记持续授权不扩展到跨书综合。综合可用亲读或AI章节笔记作为依据，但必须标明来源类型。只有用户对具体综合另行授权才能发布。
7. 完读误记被纠正时停止相关批次，标 `needs-review` 并追加更正事件，通知用户；不要删除旧事件或静默重排已交付批次。计数恢复后由责任人复核再继续。
