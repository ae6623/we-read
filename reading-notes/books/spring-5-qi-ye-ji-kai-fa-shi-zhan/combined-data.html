  • Spring让开发人员有更多的精力投入到业务逻辑开发中，而不需要将其应用程序绑定到特定的部署环境，是为了降低企业应用开发的复杂性而创建的。

3.2 AOP概述

  • 织入是把切面作用到目标对象，然后产生一个代理对象的过程。
  • 横切关注点可以对某些方法进行拦截，拦截后对原方法进行增强处理。
  • 连接点是在程序执行过程中某个特定的点，比如某方法调用的时候或者处理异常的时候。由于Spring只支持方法类型的连接点，所以在Spring AOP中一个连接点总是表示一个方法的执行。
  • 切面就是对横切关注点的抽象，这个关注点可能会横切多个对象。
  • 目标对象，被一个或者多个切面所通知的对象，即业务中需要进行增强的业务对象。

核心追问（来自深读）

Spring 5 为什么要用「响应式编程」（WebFlux）来补传统 Spring MVC 的短板？

传统 Spring MVC 基于 Servlet 的「一请求一线程」模型，在大量并发连接、尤其 I/O 等待密集时线程会被阻塞耗尽。本书第6—7章专讲 WebFlux 响应式编程与调试，第4—5章概述 Spring 5 与 Java 8 新特性，底层动机就是用非阻塞、带背压（back-pressure）的响应式流扛高并发。书里给的定位是「降低企业应用开发复杂度」——响应式不是取代 MVC，而是在长连接、流式数据这类场景补上一条异步链路。判断要不要上 WebFlux，关键看瓶颈是不是线程阻塞而非 CPU。

控制反转（IoC）、依赖倒置（DIP）、依赖注入（DI）三者到底什么关系，为什么总被混淆？

本书第18章「2.1 IoC容器揭秘」一条高划线（60人）把关系讲得很清楚：控制反转是一种软件设计模式，其遵循了依赖倒置原则；依赖注入是 Spring 框架实现控制反转的一种方式。换句话说，DIP 是原则（高层不依赖低层细节），IoC 是把「谁来控制对象创建」这个动作反转的模式，DI 则是 Spring 具体执行 IoC 的手段——通过描述（配置/注解）让容器把依赖注入进来。同章另一条划线（26人）追问「控制：由谁控制，控制了什么？」，答案正是：容器控制对象的生命周期与装配，业务代码不再自己 new 对象。

AOP 里的「横切关注点」「织入」到底解决了什么工程痛点？

第25章「3.2 AOP概述」两条高划线（各45人）点明：横切关注点可以对某些方法进行拦截，拦截后对原方法进行增强处理；织入是把切面作用到目标对象，然后产生一个代理对象的过程。工程痛点是日志、事务、鉴权这类逻辑横穿多个业务模块，若写进每个方法就造成严重重复与耦合。AOP 把这些「横切」逻辑抽成切面，在编译期/类加载期/运行期「织入」，业务代码保持纯净。配合第10—19章集成的 MyBatis、Redis、Dubbo 等，AOP 常被用来做统一缓存、分布式事务与链路追踪。

这本书到底在讲什么，适合谁看？

副标题「企业级开发实战」已说明定位：它不是 Spring 概念入门书，而是把 Spring 5 与一整套企业级中间件串起来落地的「集成手册」。全书19章，前9章讲环境、IoC/AOP 原理、Java 8 与 Kotlin 新特性、WebFlux；后10章把 Log4j2、Spring MVC、MyBatis、Redis、ZooKeeper、Kafka、Mycat、Sharding-JDBC、Dubbo 逐个集成。适合已会 Java、需要在生产项目里真正用起 Spring 生态的开发者。划线里反复出现的「降低复杂性」可视为全书价值观主线。

为什么书里既讲 Spring MVC 又讲 WebFlux，两者怎么选？

因为生态里两套并发模型并存。MVC 适合传统请求—响应、CPU/简单 I/O 的 Web 服务；WebFlux 适合高并发、长连接、背压敏感的场景（如实时推送、网关）。本书第4—5章概述新特性、第6—7章专讲 WebFlux 开发调试，说明作者认为响应式是 Spring 5 的重要增量而非噱头。推断：选型要看团队是否接受函数式/响应式思维与调试成本，不要为「新」而新，否则徒增复杂度。

学完这本书，最该带走的能力是什么？

不是记住某个注解，而是建立「用 Spring 把组件解耦并组装成系统」的工程能力。从 IoC 容器（谁控制、控制什么）、DI（如何注入）、AOP（如何无侵入增强），到把 Redis/Kafka/Dubbo 等外部系统通过 Spring 抽象层接进来，核心是「声明式 + 约定」替代硬编码。划线 [28] 说 Spring 让开发者「更多投入业务逻辑，不绑定特定部署环境」，正是对这种能力的概括。

用更高维度的知识看这本书

把本书放回技术谱系：它处在 Spring 从「轻量级容器」演进到「全家桶式微服务底座」的节点上。Spring 5（2017）与 Java 8 的基线，使响应式（Reactor 底层）、函数式 Bean 注册、Kotlin 支持成为可能；本书把这些特性首次系统化地与中国企业常用中间件（Redis、Kafka、Dubbo、ZooKeeper、Mycat/Sharding-JDBC）做集成演示，属于典型的「本土工程化」著作。

参照价值上，它与 Craig Walls 的《Spring 实战》（同列书单）互补：后者偏官方指南、循序渐进，本书偏集成清单、实战排障。局限在于这类「版本速写」型图书半衰期短——Spring Boot 与 Spring Cloud 的快速迭代会让后10章的具体配置在数年里过时，长期可复用的是前9章的 IoC/AOP/响应式思想。读它应把它当「集成地图」而非「权威规范」。

阅读时要验证的问题

  • 本书集成的中间件（Kafka/ZooKeeper/Dubbo/Mycat 等）版本与其发布时一致，跨版本配置可能已变，落地前以各组件当前官方文档为准。
  • WebFlux 的「非阻塞提升性能」只在 I/O 密集型场景成立；CPU 密集型业务上响应式反而增加复杂度，勿盲信「响应式更快」。
  • 划线数据来自微信读书读者，反映「学习热点」而非技术权重；IoC/AOP 划线高更多因其是全书基础概念被反复阅读。
  • 书中具体 XML/注解示例请以随书源码仓库核对，正文与代码库在不同版本间可能有出入。

当年与今天 · 初步对照

本书出版于 Spring 5 / Java 8 时代，彼时「响应式」还是新鲜词、Kotlin 支持刚落地。今天 Spring 6 已要求 Java 17 基线、Jakarta EE 命名空间，WebFlux 与 R2DBC 走向成熟，而 Dubbo/Seata 等国产中间件生态也更完整。当年书里「企业级集成」的痛点（分库分表、消息解耦、服务治理）如今多由 Spring Cloud Alibaba 一站式缓解。

真正没变的是底层范式：IoC 把「对象生命周期」交给容器、AOP 把「横切逻辑」与业务解耦、约定优于配置——这三条仍是今天 Spring Boot 自动配置的思想内核。变化的是工具链：当年要手写大量集成代码，如今 starter 与自动配置几行依赖即可。读它的当下价值，是借 2017 年的「全家桶拼装」理解今天「开箱即用」背后的原理。
