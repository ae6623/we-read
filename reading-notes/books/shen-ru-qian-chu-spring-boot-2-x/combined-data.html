6.3 隔离级别

  • 这51笔交易笔数就是多条数据库记录统计出来的。而可重复读是针对数据库的单一条记录，例如，商品的库存是以数据库里面的一条记录存储的，它可以产生可重复读，而不能产生幻读。
  • 读写提交（read committed）隔离级别，是指一个事务只能读取另外一个事务已经提交的数据，不能读取未提交的数据。
  • 在现实中一般而言，选择隔离级别会以读写提交为主，它能够防止脏读，而不能避免不可重复读和幻读。
  • 为了克服这些问题，数据库提出了事务之间的隔离级别的概念
  • 未提交读（read uncommitted）是最低的隔离级别，其含义是允许一个事务读取另外一个事务没有提交的数据。
  • 数据库事务具有以下4个基本特征，也就是著名的ACID。

6.4 传播行为

  • 在Spring中，当一个方法调用另外一个方法时，可以让事务采取不同的策略工作，如新建事务或者挂起当前事务等，这便是事务的传播行为
  • 在一个批量任务执行的过程中，调用多个交易时，如果有一些交易发生异常，只是回滚那些出现异常的交易，而不是整个批量任务，这样就能够使得那些没有问题的交易可以顺利完成，而有问题的交易则不做任何事情

核心追问（来自深读）

「约定优于配置」到底替开发者省掉了什么，又隐藏了什么？

第17章「1.3 Spring Boot 的优点」一条高划线（85人）开宗明义：「约定优于配置，这是 Spring Boot 的主导思想。」它省掉的是传统 Spring 里大量「声明式胶水」——你按约定放好目录、起好名字，Boot 就自动装配好数据源、Web 容器、事务管理器。但隐藏的是「黑箱」：当约定不满足你的特殊需求时，你得先理解它默认做了什么才能改。所以 Boot 的学习曲线是「先爽后难」——起步极快，定制时要补回被省略的配置知识（如第26章 @ComponentScan 只扫当前包与子包，36人划线即提示约定边界）。

书里对数据库「隔离级别」讲得细，为什么这是企业开发的命门？

第48章「6.3 隔离级别」两条高划线（72人、51人）点出关键区分：读写提交（read committed）只能读已提交数据；而「可重复读」针对单条记录（如商品库存那一条），能产生可重复读却不一定能避免幻读。企业开发的命门在于：并发下「脏读/不可重复读/幻读」会直接造成超卖、重复记账。本书用「51 笔交易对应多条记录、库存是单条记录」的具体例子说明隔离级别选错的危害，把抽象概念落到抢购、库存这类真实痛点——也呼应了提要里「互联网抢购业务」的实战定位。

IoC 容器「两个基本功能」和「生命周期」对写业务代码有什么实际意义？

第24章两条高划线（68人、52人）说：IoC 是通过描述生成/获取对象的技术；容器基本功能一是「通过描述管理 Bean（发布和获取）」，二是「通过描述完成 Bean 之间的依赖关系」。第28章（51人）补充生命周期四阶段：Bean 定义、初始化、生存期、销毁。实际意义是：你写的每个 @Service/@Component 何时被创建、何时注入依赖、何时销毁，都由容器掌管。理解生命周期才能正确处理资源（如连接池、NoSQL 客户端）的初始化与释放，避免内存泄漏与空指针。第27章那条「容器不知注入狗还是猫」（39人）正是提醒：依赖关系必须描述清楚，否则运行时才报错。

这本书和《Spring 实战》《Spring 5 企业级开发实战》怎么分工？

三本互补：本书（「深入浅出 Spring Boot 2.x」）偏「原理 + 国内互联网实战」——从全注解 IoC/AOP 讲到抢购、Redis、MongoDB、Spring Cloud，特别适合要从传统 Spring XML 转向 Boot 的国内工程师；另一本《Spring 5 企业级开发实战》偏「全家桶集成清单」；《Spring 实战》偏「官方循序渐进入门」。简言之：要啃 Boot 原理与分布式，读这本；要广撒网集成，读企业级实战；要打基础，读实战。

学完这本书，能独立做微服务吗？

提要列出「REST 风格和 Spring Cloud 分布式开发」是末尾内容，说明本书把微服务放在「先打好 Boot 基础」之后。你能学到 REST 端点设计（第77章，42人：每个资源对应唯一 URI/端点）、事务传播（第49章，51人）、用 Boot 快速搭服务。但微服务真正难点（服务发现、配置中心、熔断、链路追踪、数据一致性）只点到即止。推断：本书让你「能起步做单体式 Boot 服务并向微服务过渡」，完整微服务仍需补 Spring Cloud 专项资料。

书里为什么专门讲「互联网抢购业务」？

因为它是检验 Spring Boot 企业级能力的最佳场景：高并发下要保证库存不超卖（靠事务隔离级别与锁）、响应要快（靠缓存 Redis、异步）、系统要稳（靠监控与降级）。抢购把本书前半部分的 IoC、事务、NoSQL、WebFlux 全部串成一条实战链路。对国内互联网开发者而言，这比泛泛讲「企业应用」更对症下药，也体现作者「内容紧扣互联网企业实际要求」的写法取向。

用更高维度的知识看这本书

本书出版于 2018 年 3 月 Boot 2.x 发布之际，是国内第一批系统讲解 Boot 2.x 的中文著作之一。它承接「Spring Boot 让 Spring 落地变简单」的浪潮，把关注点从「如何用」推进到「原理与陷阱」——大量篇幅给 IoC 生命周期、事务隔离、传播行为这些「看不见但会出事」的地带，定位接近「进阶实战手册」。

参照上，它与国外《Spring Boot in Action》同源但更贴国内栈（Redis/MyBatis/Dubbo 味重）；局限是 2.x 时代的 API 在 3.x（Java 17、Jakarta）下已有迁移成本，部分示例会过时。读它应重点吸收「约定优于配置」「理解容器而非只看注解」的元认知——这些原则跨版本有效，而具体 starter 配置则需对照新版文档更新。

  • 本书基于 Spring Boot 2.x（2018），部分 API 与配置在 3.x（Java 17 基线、Jakarta 命名空间）下已变，落地以当前版本文档为准。
  • 隔离级别（可重复读/幻读）的行为依赖具体数据库引擎（如 MySQL InnoDB 对可重复读的实现包含防幻读），书中例子以通用语义讲解，跨库需核实。
  • 划线数据来自微信读书读者，反映学习热点而非技术权重；如 IoC/事务划线高，因它们是 Boot 基础被反复研读。
  • 「约定优于配置」会隐藏默认行为，团队应补写关键约定的文档，避免「黑箱出事才查」。

当年与今天 · 初步对照

本书写于 Boot 2.x 普及期，彼时「微服务」「互联网高并发」是招聘热词，书里抢购、Redis、Spring Cloud 正对风口。今天 Boot 3.x 已成新基线，自动配置与 starter 生态更成熟，「手写大量集成」的痛苦大幅缓解，但「理解容器与事务本质」的需求一点没减。

不变的是 Boot 的核心契约：约定优于配置（第17章，85人）、容器掌管 Bean 生命周期（第24/28章）。变化的是复杂度转移——从「怎么配」转向「怎么在云上观测与弹性」。可迁移的启发：任何「开箱即用」框架，真正值钱的不是会用注解，而是懂它在背后替你做了什么、以及做错时怎么改。这条对今天任何低代码/AI 生成代码的场景都成立。
