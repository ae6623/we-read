第1章 Spring起步

  • 唯一不变的就是变化

1.1 什么是Spring

  • 因为Spring XML配置是一种过时的方式，所以我们主要关注Spring基于Java的配置。
  • 任何实际的应用程序都是由很多组件组成的，每个组件负责整个应用功能的一部分，这些组件需要与其他的应用元素进行协调以完成自己的任务。当应用程序运行时，需要以某种方式创建并引入这些组件。
  • 在Spring技术中，自动配置起源于所谓的自动装配（autowiring）和组件扫描（component scanning）。
  • Spring Boot能够基于类路径中的条目、环境变量和其他因素合理猜测需要配置的组件并将它们装配在一起。
  • 在历史上，指导Spring应用上下文将bean装配在一起的方式是使用一个或多个XML文件（描述各个组件以及它们与其他组件的关联关系）
  • 没有代码就是自动装配的本质，也是它如此美妙的原因所在。
  • 即便如此，不管是使用Java还是使用XML的显式配置，只有当Spring不能进行自动配置的时候才是必要的
  • 将bean装配在一起的行为是通过一种基于依赖注入（dependency injection，DI）的模式实现的。
  • @Configuration注解会告知Spring这是一个配置类，会为Spring应用上下文提供bean。
  • Spring Boot大幅度减少了构建应用所需的显式配置的数量（不管是XML配置还是Java配置）。
  • 默认情况下，这些bean所对应的bean ID与定义它们的方法名称是相同的
  • 就像砖块、砂浆、木材、管道和电线组合在一起，形成一栋房子似的

  • 在开发应用程序代码时，我们可以编写两种风格的代码，即命令式和反应式。

10.1 反应式编程概览

  • 反应式流旨在提供无阻塞回压的异步流处理标准
  • 虽然创建线程很简单，但是这些线程多半最终会被阻塞。管理多线程中的并发极具挑战，而更多线程则意味着更多的复杂性
  • 通过回压，数据消费者可以限制它们想要处理的数据数量，避免被过快的数据源所淹没。

10.2 初识Reactor

  • Flux代表具有零个、一个或者多个（可能是无限个）数据项的管道。Mono是一种特殊的反应式类型，针对数据项不超过一个的场景，它进行了优化。

11.1 使用Spring WebFlux

  • 与其将反应式编程模型硬塞进Spring MVC中，还不如创建一个单独的反应式Web框架，并尽可能多地借鉴Spring MVC。这样，Spring WebFlux就应运而生了
  • Spring WebFlux是真正的反应式Web框架，允许在事件轮询中处理请求；而Spring MVC是基于Servlet的，依赖于多线程来处理多个请求

《Spring 实战》第5版为什么把 Spring Boot 2.0 提到和 Spring 5.0 同等核心的位置？

提要明说第5版「涵盖了Spring 5.0 和Spring Boot 2.0 里程碑式的更新」，并用第1—4部分铺陈「基础→集成→反应式→微服务」。背后判断是：Spring 早不只是 IoC 容器，而是以 Boot 为入口、以 Spring Cloud 为分布式延伸的生态。第1章划线（119人）说「Spring XML 配置是一种过时的方式，我们主要关注 Spring 基于 Java 的配置」——Boot 的自动配置正是 Java 配置思想的集大成，把过去一大堆 XML/注解收敛成 @SpringBootApplication 这一个组合注解（第10章，144人）。所以第5版本质是「用 Boot 重写 Spring 学习路径」。

书里反复说「任何实际应用都由很多组件组成、需要协调」，这到底在强调什么设计观？

第1章「什么是 Spring」（112人）一条高划线点明：任何实际应用都由很多组件组成，每个组件负责整体功能的一部分，运行时需要以某种方式创建并引入这些组件。这强调「组合优于单体、协作优于硬编码」的工程观——Spring 的价值不是帮你写一个类，而是把几十上百个类「装配」成能跑的系统。它呼应 IoC：组件的创建与依赖关系交给容器，业务代码只声明自己需要什么。这也是为什么全书从「初始化应用」（第10章）讲起，因为 Boot 第一步就是把组件树搭起来。

「反应式编程」在本书里被放在第3部分单独成篇，它真有那么重要吗？

书里给的定位是第3部分「探讨 Spring 对反应式编程提供的全新支持」，并配了一条明确划线（60人）：反应式编程「致力于通过非阻塞操作提供更好的扩展性并提升性能」。更技术的定义在第10章概览（68人）：反应式流旨在提供「无阻塞回压的异步流处理标准」。所以作者认为它重要，是因在流式、高并发 I/O 场景下，传统阻塞模型会成瓶颈，反应式是 Spring 5 的关键增量。但也要看场景——它解决的是扩展性边界问题，不是银弹。

AI 问书

以下问答依据本书全书提要、章节结构与热门划线原文整理，不虚构页码；标「推断」处为整理者补注。

这本书跟同名的「Spring 5 企业级开发实战」有什么不同，怎么选？

定位不同：本书（Craig Walls 著、第5版）是「经典学习指南」，强调循序渐进、概念清晰，适合「刚开始学 Spring Boot 和 Spring 框架的 Java 开发人员快速上手」，也照顾想学新特性的老手；而另一本是「企业级集成实战」，偏中间件清单与排障。简言之：要系统打基础、理解 Spring 为什么这么设计，读这本；要直接把 Redis/Kafka/Dubbo 接进生产，读那本。两本互补，不冲突。

学这本书，最重要的「第一个动作」是什么？

第1章「Spring 起步」和「初始化 Spring 应用」（第10章，144人）给出的起点是：认识 @SpringBootApplication 这个组合注解——它组合了三个注解，一键开启自动配置、组件扫描与 Boot 引导。划线里那句轻松的「如果你不是 Spring Tool Suite 用户，那也没有关系，我们依然可以做朋友」（112人）也暗示：工具不重要，理解注解背后发生了什么才重要。第一个动作应是跑通一个最小 Boot 应用，再看它自动装配了哪些 Bean。

书里对「配置管理」给了什么实用建议？

几条高划线都集中在「环境隔离」：第34章说激活 prod profile 后，对应属性比默认 profile 优先级更高（54人）；第19章提醒「部署到生产环境之前，一定要删除这一行代码（或设为 true）」（54人），指关闭开发期开关（如错误页 detail）。第22章还讲 schema.sql 在根类路径下会在启动时自动执行（108人）。核心建议是：用 profile 把环境差异外置，别把开发期方便留到生产。

用更高维度的知识看这本书

本书是 Spring 官方生态里最畅销的「官方色彩」入门书（作者 Craig Walls 长期参与 Spring 社区），第5版（2017—2018）正值 Spring 5 + Spring Boot 2 的重大分水岭：Java 8 基线、响应式 Spring WebFlux 首次成体系进入教程。它把「学 Spring」重新定义为「学 Boot 驱动的应用」，对国内大量「从 XML 时代过来」的开发者完成了一轮认知迁移。

参照上，它与 Rob Harrop 等早期《Spring 高级》不同，走「平易近人」路线（书中「我们依然可以做朋友」的幽默即风格体现）。局限是「实战」二字偏基础：分布式事务、可观测性、安全合规等生产深水区仅在第5部分「部署」浅尝。读它应与 Spring 官方文档、以及《Spring 5 企业级开发实战》（同列书单）配合，前者建立直觉，后者补足工程细节。

阅读时要验证的问题

  • 第5版内容绑定 Spring 5 / Boot 2 的具体 API，部分示例（如 schema.sql 自动执行、profile 优先级）在新版本行为可能微调，落地以当前版本文档为准。
  • 「XML 配置过时」是作者在该书语境下的主张，并非 Spring 已移除 XML 支持；遗留系统仍大量使用，勿据此否定 XML。
  • 划线热度反映读者学习轨迹（入门概念被反复读），不代表技术重要性排序。
  • 反应式「提升性能」只在非阻塞 I/O 场景成立，书中表述需结合上下文理解，勿作普适结论引用。

当年与今天 · 初步对照

第5版写于 2018 年前后，彼时 Spring Boot 2 刚发布、响应式还是「进阶话题」。今天 Spring Boot 3（Java 17 基线、Jakarta 命名空间）已成默认选择，自动配置与 starter 极其成熟，当年要专门讲「初始化应用」「组合注解」的内容，如今已是开发者的肌肉记忆。

不变的主线仍是「组件组合 + 约定优于配置 + 环境外置」（prod profile、schema.sql 等划线至今有效）。变化的是心智负担大幅降低——云原生让部署从「手动打包」变成「镜像 + 平台」。可迁移的启发：无论框架怎么进化，先想清楚「应用由哪些组件组成、它们如何协作」（第1章，112人），永远是设计好系统的起点。
