3第1章 快速入门›

3 个小节 · 10 句热门划线

1.1 消息队列功能介绍

  • 数据的产生方只需要把各自的数据写入一个消息队列即可，数据使用方根据各自需求订阅感兴趣的数据，不同数据团队所订阅的数据可以重复也可以不重复，互不干扰，也不必和数据产生方关联。
  • 通过利用消息队列，把大量的请求暂存起来，分散到相对长的一段时间内处理，能大大提高系统的稳定性和用户体验。
  • 分布式消息队列可以提供应用解耦、流量消峰、消息分发等功能，已经成为大型互联网服务架构里标配的中间件。
  • 如果有消息队列做缓冲，我们可以取消这个限制，把一秒内下的订单分散成一段时间来处理，这时有些用户可能在下单后十几秒才能收到下单成功的状态，但是也比不能下单的体验要好。
  • 应用解耦、流量消峰、消息分发等功能外，消息队列还有保证最终一致性、方便动态扩容等功能。
  • 当物流系统恢复后，补充处理存储在消息队列里的订单信息即可，终端用户感知不到物流系统发生过几分钟的故障。
  • 使用消息队列进行流量消峰，很多时候不是因为能力不够，而是出于经济性的考量。
  • 消息队列已经成为数据处理系统不可或缺的一部分

1.2 RocketMQ简介

  • RocketMQ是使用Java语言开发的，比起Kafka的Scala语言和RabbitMQ的Erlang语言，更容易找到技术人员进行定制开发。

1.3 快速上手RocketMQ

  • 启动单机的消息队列服务比较简单，不需要写配置文件，只需要依次启动本机的NameServer和Broker即可。

5第3章 用适合的方式发送和接收消息›

3 个小节 · 15 句热门划线

3.1 不同类型的消费者

  • 长轮询方式的局限性，是在HOLD住Consumer请求的时候需要占用资源，它适合用在消息队列这种客户端连接数可控的场景中。
  • RocketMQ支持两种消息模式：Clustering和Broadcasting。
  • 这是通过“长轮询”方式达到Push效果的方法，长轮询方式既有Pull的优点，又兼具Push方式的实时性
  • 需要注意的是Offset的保存，要在程序的异常处理部分增加把Offset写入磁盘方面的处理，记准了每个Message Queue的Offset，才能保证消息消费的准确性。
  • 在Broadcasting模式下，同一个ConsumerGroup里的每个Consumer都能消费到所订阅Topic的全部消息，也就是一个消息会被多次分发，被多个Consumer消费。
  • PushConsumer会判断获取但还未处理的消息个数、消息总大小、Offset的跨度，任何一个值超过设定的大小就隔一段时间再拉取消息，从而达到流量控制的目的。
  • “长轮询”的核心是，Broker端HOLD住客户端过来的请求一小段时间，在这个时间内有新消息到达，就利用现有的连接立刻返回消息给Consumer。
  • “长轮询”方式通过Client端和Server端的配合，达到既拥有Pull的优点，又能达到保证实时性的目的。
  • 此外ProcessQueue还可以辅助实现顺序消费的逻辑。
  • Consumer的GroupName用于把多个Consumer组织到一起，提高并发处理能力，GroupName需要和消息模式（MessageModel）配合使用。
  • 如果不需要消费某个Topic下的所有消息，可以通过指定消息的Tag进行消息过滤
  • 随着不断读取消息，Offset会不断增长。这个时候由用户负责把Offset存储下来，根据具体情况可以存到内存里、写到磁盘或者数据库里等。

3.2 不同类型的生产者

  • 写一个高质量的生产者程序，重点在于对发送结果的处理，要充分考虑各种异常，写清对应的处理逻辑。
  • RocketMQ支持发送延迟消息，Broker收到这类消息后，延迟一段时间再处理，使消息在规定的一段时间后生效。

3.3 如何存储队列位置信息

  • Offset是指某个Topic下的一条消息在某个Message Queue里的位置，通过Offset的值可以定位到这条消息，或者指示Consumer从这条消息开始向后继续处理。
6第4章 分布式消息队列的协调者›

3 个小节 · 7 句热门划线

  • NameServer的存在主要是为了解决这类问题，由NameServer维护这些配置信息、状态信息，其他角色都通过NameServer来协同执行。

4.1 NameServer的功能

  • NameServer中的Broker、Topic等状态信息不会持久存储，都是由各个角色定时上报并存储到内存中的
  • ClusterAddrTable 存储的是集群中Cluster的信息，结果很简单，就是一个Cluster名称对应一个由BrokerName组成的集合。
  • NamServer可以部署多个，相互之间独立，其他角色同时向多个NameServer机器上报状态信息，从而达到热备份的目的。

4.2 各个角色间的交互流程

  • 中间件对稳定性要求很高，RocketMQ的NameServer只有很少的代码，容易维护，所以不需要再依赖另一个中间件，从而减少整体维护成本
  • ZooKeeper的功能很强大，包括自动Master选举等，RocketMQ的架构设计决定了它不需要进行Master选举，用不到这些复杂的功能，只需要一个轻量级的元数据服务器就足够了。

4.4 本章小结

  • NameServer的功能虽然非常重要，但是被设计得很轻量级，代码量少并且几乎无磁盘存储，所有的功能都通过内存高效完成
7第5章 消息队列的核心机制›

4 个小节 · 7 句热门划线

5.1 消息存储和发送

  • RocketMQ充分利用了上述特性，也就是所谓的“零拷贝”技术，提高消息存盘和网络发送的速度
  • 目前的高性能磁盘，顺序写速度可以达到600MB/s，超过了一般网卡的传输速度，这是磁盘比想象的快的地方。但是磁盘随机写的速度只有大概100KB/s，和顺序写的性能相差6000倍！

5.2 消息存储结构

  • 虽然是随机读，但是利用操作系统的pagecache机制，可以批量地从磁盘读取，作为cache存到内存中，加速后续的读取速度。

5.5 同步复制和异步复制

  • 应该把Master和Save配置成ASYNC_FLUSH的刷盘方式，主从之间配置成SYNC_MASTER的复制方式
  • 同步复制方式是等Master和Slave均写成功后才反馈给客户端写成功状态；异步复制方式是只要Master写成功即可反馈给客户端写成功状态
  • 有些数据因为没有被写入Slave，有可能会丢失

5.6 本章小结

  • RocketMQ基于“顺序写”“随机读”的原则来设计，利用“零拷贝”技术，克服了磁盘操作的瓶颈
8第6章 可靠性优先的使用场景›

3 个小节 · 5 句热门划线

6.1 顺序消息

  • 在发送端，要做到把同一业务ID的消息发送到同一个Message Queue；在消费过程中，要做到从同一个Message Queue读取的消息不被并发处理，这样才能达到部分有序
  • 保证全局顺序消息，需要先把Topic的读写队列数设置为一，然后Producer和Consumer的并发设置也要是一。

6.2 消息重复问题

  • 解决消息重复有两种方法：第一种方法是保证消费逻辑的幂等性（多次调用和一次调用效果相同）；另一种方法是维护一个已消费消息的记录，消费前查询这个消息是否被消费过。这两种方法都需要使用者自己实现。

6.3 动态增减机器

  • 第4种方式看似繁琐，但它是唯一支持动态增加NameServer，无须重启其他组件的方式。使用这种方式后其他组件会每隔2分钟请求一次该URL，获取最新的NameServer地址。
  • 集群扩容后，一是可以把新建的Topic指定到新的Broker机器上，均衡利用资源；另一种方式是通过updateTopic命令更改现有的Topic配置，在新加的Broker上创建新的队列

核心追问（来自深读）

RocketMQ 的整体角色模型是怎样的，为什么这样划分？

书里用类比把四个角色讲得很清楚：发信者、收信者、暂存传输的邮局、协调各邮局的管理机构，对应到 RocketMQ 就是 Producer、Consumer、Broker、NameServer。Producer 生产消息，Consumer 消费消息，Broker 负责存储与转发，NameServer 作为轻量注册/路由中心让生产者和消费者找到对应的 Broker。这种“生产—消费—存储—路由”的四元模型，把消息系统的职责拆得干净：Broker 专注持久化与投递，NameServer 专注寻址，彼此解耦，正是 RocketMQ 能做到高吞吐、易扩展的结构基础。

书里说“消息重复”有两种解法，背后的前提是什么？

划线里作者给出两种：一是保证消费逻辑的幂等性（多次调用与一次调用效果相同），二是维护已消费消息记录、消费前查询是否消费过；且两种都需使用者自己实现。前提是 RocketMQ 的投递语义是“至少一次（at least once）”，而非“恰好一次”——网络重试、主从切换、客户端重投都会造成重复。框架把“不丢”做得很稳，却把“不重”的责任交还给业务，因为是否重复只业务自己能判定。所以幂等设计（如用业务唯一键去重）是使用 RocketMQ 几乎必做的功课。

为什么说“顺序消息”需要把同一业务 ID 发到同一个 Message Queue？

划线指出：发送端要把同一业务 ID 的消息发到同一个 Message Queue，消费时从同一 Message Queue 读取的消息不被并发处理，才能达到部分有序。原因是 RocketMQ 的“顺序”保证在单个队列内——队列本身是 FIFO 的，只要相关消息落在同一队列、且消费端单线程处理该队列，顺序就不会乱。跨队列则无法保证全局顺序。这是一种“分片有序”的设计：用业务 ID 做哈希路由到固定队列，在“局部有序”与“水平扩展”之间取得平衡，而非追求代价高昂的全局有序。

“长轮询”消费方式有什么权衡？

划线提到长轮询的局限性：在 HOLD 住 Consumer 请求时需要占用资源，它适合用在消息队列这种客户端连接数可控的场景。长轮询是 RocketMQ 实现“准实时推送”的方式——Broker 在没有消息时不立即返回，而是挂起请求直到有消息或超时，从而兼顾实时性与拉模式的简洁。代价是占用连接与线程；但因为消息队列的客户端数通常远小于终端用户数，这种资源占用是可控的。对比纯推或纯拉，长轮询是面向“少量长连客户端”的折中优选。

主从复制/刷盘的配置（ASYNC_FLUSH + SYNC_MASTER）在讲什么权衡？

划线建议：Master 和 Slave 都配置 ASYNC_FLUSH（异步刷盘），主从之间配置 SYNC_MASTER（同步复制）。这组合的含义是——本地写盘异步（追求写入吞吐，掉电可能丢少量已应答消息），但主从数据同步复制（保证从节点与主节点一致，主宕机不丢数据）。权衡点是：用“可容忍的本地丢失风险”换“高写入性能 + 主从强一致”。生产里具体选 ASYNC 还是 SYNC 刷盘，取决于你对“丢消息”与“延迟/吞吐”的容忍度，没有绝对正确的答案。

把 RocketMQ 放回消息中间件演进史：它脱胎于阿里内部（MetaQ/Notify）对高可靠、高吞吐交易消息的需求，2012 年开源、2016 年捐赠 Apache 孵化并于 2017 年毕业，与 Kafka（日志流）、RabbitMQ（AMQP）、Pulsar（存算分离）形成对照。RocketMQ 的强项是“金融级可靠 + 事务消息 + 低延迟”，其设计明显带着电商交易场景的烙印——这也是书里反复强调“不丢、幂等、有序”的原因。

需要补的外部视角：消息队列的语义分级（至多一次/至少一次/恰好一次）是分布式系统的经典难题，业界的“恰好一次”多靠“幂等 + 去重 + 事务消息”近似实现，而非框架魔法。RocketMQ 的事务消息（半消息机制）即是一例。读本书应把它置于“分布式一致性”的大问题下理解——消息系统不是在真空中提速，而是在“可靠 vs 性能”的光谱上选点。对比 Kafka 的吞吐优先、Pulsar 的分层存储，方能看清 RocketMQ 的取舍。

阅读时要验证的问题

  • “Message Queue 数设为 16”是作者经验值，实际应按分区并行度与消费并发调整，并非万能常数。
  • “RocketMQ 用 Java 更易定制”是相对 Kafka(Scala)/RabbitMQ(Erlang) 的便利，但定制仍需吃透源码，勿低估门槛。
  • SYNC_MASTER + ASYNC_FLUSH 能在主宕机时保一致，但极端断电仍可能丢已 ACK 消息，引用“不丢”前说明边界。
  • 消息重复的解法（幂等/去重表）需业务侧实现，框架只保证不丢，引用“至少一次”语义时务必点明责任归属。

当年与今天 · 初步对照

本书写作时，RocketMQ 刚毕业为 Apache 顶级项目，国产中间件“自主可控”叙事正盛；今天，它已广泛应用于电商、金融、IoT 等场景，并与云厂商托管服务深度绑定。当年需要手敲的部署、监控、管理命令，如今多被控制台与 SaaS 封装。书里强调的“少踩坑”经验，在托管时代价值不减——因为坑的本质（顺序、重复、积压）是消息模型的固有性质，与是否上云无关。

对当下读者的迁移启示：消息队列的核心考题从未改变——可靠性、顺序性、幂等、积压治理。学 RocketMQ，学的不只是某个 broker 配置，而是“用异步解耦系统时，如何为失败与重复买单”的工程思维。在事件驱动架构、CQRS、流处理当道的今天，这套思维比任何具体命令都更保值。记住：框架承诺“不丢”，但“不重”永远是你自己的作业。
