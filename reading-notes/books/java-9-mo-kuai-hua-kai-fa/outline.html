第一部分 Java模块系统介绍

模块化概述

  • 模块化是用来管理和减少大型代码库复杂性的技术之一
    • Java 9引入了一个新的模块系统，从而可以更容易地创建和访问模块。
  • Java模块系统对Java开发产生了深刻的影响
    • 它代表了模块化成为整个Java平台高级功能这一根本转变，从根本上解决了模块化的问题，对语言、JVM(Java Virtual Machine, Java虚拟机)以及标准库都进行了更改。

什么是模块化

  • 模块化是指将系统分解成独立且相互连接的模块的行为
    • 模块是包含代码的可识别工件，使用了元数据来描述模块及其与其他模块的关系。
  • 模块必须遵循强封装性、定义良好的接口和显式依赖三个核心原则
    • 强封装性：一个模块必须能够对其他模块隐藏其部分代码。
    • 定义良好的接口：虽然封装是很好的做法，但如果模块需要一起工作，那么就不能将所有的内容都进行封装。
    • 显式依赖：一个模块通常需要使用其他模块来完成自己的工作，这些依赖关系必须是模块定义的一部分，以便使模块能够独立运行。

在Java 9之前

  • Java可用于开发各种类型和规模的应用程序，但存在一些模块化的问题
    • 通过组合使用包(package)和访问修饰符(比如private、protected或public)，可以实现类型封装，但这样做会产生一个问题：如果想从组件的另一个包中访问该类，同时仍然防止其他类使用该类，那么应该怎么做呢？事实是无法做到。
    • 在定义良好接口方面，Java自诞生以来就一直做得很好。
    • 显式依赖是事情开始出问题的地方。Java确实使用了显式的import语句。但不幸的是，从严格意义上讲，这些导入是编译时结构，一旦将代码打包到JAR中，就无法确定哪些JAR包含当前JAR运行所需的类型。
  • Maven和OSGi是管理依赖关系的外部工具
    • Maven构建工具所解决的一个问题是实现编译时依赖关系管理。
    • OSGi要求将导入的包在JAR中列为元数据，称之为捆绑包(bundle)。此外，还必须显式定义导出哪些包，即对其他捆绑包可见的包。

Java 9模块

  • Java 9模块系统的主要目标是将JDK本身进行模块化和提供一个应用程序可以使用的模块系统
    • JDK的模块化可通过使用与应用程序开发人员在Java 9中使用的相同的模块系统来实现。
  • 模块系统将模块的本质概念引入Java语言和运行时
    • 模块既可以导出包，也可以强封装包。
    • 此外，它们显式地表达了与其他模块的依赖关系。
  • Java平台模块系统带来了可靠配置、强封装型、可扩展开发、安全性和优化等好处
    • 可靠的配置：在编译或运行代码之前，模块系统会检查给定的模块组合是否满足所有依赖关系，从而导致更少的运行时错误。
    • 强封装型：模块显式地选择了向其他模块公开的内容，从而防止对内部实现细节的意外依赖。
    • 可扩展开发：显式边界能够让开发团队并行工作，同时可创建可维护的代码库。
    • 安全性：在JVM的最深层次上执行强封装，从而减少Java运行时的攻击面，同时无法获得对敏感内部类的反射访问。
    • 优化：由于模块系统知道哪些模块是在一起的，包括平台模块，因此在JVM启动期间不需要考虑其他代码。同时，其也为创建模块分发的最小配置提供了可能性。
第2章 模块和模块化JDK

Java模块系统的背景和目标

  • JDK的运行时库由一个庞大的rt.jar所组成，包含Java大部分运行时类
    • JDK的rt.jar中仍然存在支持CORBA的类，无论运行什么应用程序，Java的每次发布都会包含这些CORBA类。
  • JDK团队着手对JDK进行模块化，以获得一个灵活且符合未来发展方向的平台
    • 模块化JDK的目标之一是删除过时的技术，减少不必要的磁盘空间、内存和CPU时间。
    • 模块化JDK的另一个目标是将JDK分解成模块，以便于理解和维护。

模块化JDK的实现

  • Java 8中采用了紧凑型配置文件，定义了标准库中可用于针对该配置文件的应用程序的一个包子集
    • 使用这些预定义配置文件更新Java编译器和运行时。
  • JDK 9被拆分为大约90个平台模块，每个平台模块都构成了JDK的一个定义良好的功能块
    • 所有模块都显式地定义了与其他模块的依赖关系。
    • 模块系统不允许模块之间存在编译时循环依赖。

模块描述符

  • 模块拥有一个名称，并对相关的代码以及可能的其他资源进行分组，同时使用一个模块描述符进行描述
    • 模块描述符保存在一个名为module-info.java的文件中。
  • 模块描述符可以包含exports语句，强封装性是模块的默认特性
    • 只有当显式地导出一个包时，才可以从其他模块中访问该包。

可读性和可访问性

  • 可读性是指一个模块可以读取其他模块，读取其他模块意味着可以访问其导出包中的类型
    • 可以在模块描述符中使用requires子句设置模块之间的可读性关系。
  • 可访问性在编译时和运行时被强制执行，可访问性和可读性的结合可以确保在模块系统中实现强封装性
    • 是否可以在模块M1中访问模块M2中的类型已经成为一个双重问题：M1是否可以读取M2？如果可以，M2导出包中的类型是否可以访问？
    • 在模块出现之前，强封装实现类的唯一方法是将这些类放置到单个包中，并标记为私有。通过使用模块，可以以任何方式构建包，并仅导出模块使用者真正必须访问的包。

隐式可读性

  • 默认情况下，可读性是不可传递的，但可以通过requires transitive实现可传递的可读性
    • 对于java.sql，可完成如下修改：module java.sql { requires transitive java.logging; requires transitive java.xml; exports java.sql; exports javax.sql; exports javax.transaction.xa; }。
  • 隐式可读性自身也是可传递的
    • 以平台中另一个聚合器模块java.se.ee为例。从图2-1可以看到，相比于java.se, java.se.ee聚合了更多的模块。它使用了requires transitive java.se并添加了多个模块(包含了Java EE规范的部分内容)。

限制导出

  • 限制导出允许将包暴露给特定的某些模块
    • 可以在java.xml模块中找到限制导出的示例：module java.xml { exports com.sun.xml.internal.stream.writers to java.xml.ws; }。

模块解析和模块路径

  • 模块是从模块路径中解析出来的，而不是类路径
    • 当编译和运行模块时，Java编译器和运行时使用模块描述符来解析正确的模块。
  • 模块解析是根据给定的依赖关系图并从该图中选择一个根模块来计算最低需求的模块集的过程
    • 从根模块可访问的每个模块最终都在解析模块集中。

在不使用模块的情况下使用模块化JDK

  • Java 9可以像以前的Java版本一样使用，而不必将代码移动到模块中
    • 当在Java 9中使用类路径时，还需要注意两件事情。首先，由于平台是模块化的，因此对内部实现类进行了强封装。其次，当在Java 9类路径上运行(而不是编译)一个应用程序时，使用了更为宽松的强封装形式。
第3章 使用模块

第一个模块

  • 创建一个简单的模块，包括模块描述符和源文件
    • 模块描述符是一个包含module关键字的Java文件，位于模块目录的根目录中。
    • 模块可能仅包含包中的类型，所以需要一个包定义。
  • 命名模块，确保名称唯一且有意义
    • 模块名称必须是唯一的：应用程序只能具有一个给定名称的模块。
    • 对于应用程序模块来说，要尽量选择更短且更令人难忘的名称。
  • 编译模块，生成分解模块格式
    • 在要编译的文件集中出现module-info.java源文件会触发javac的模块感知模式。
    • 编译后的结果，也被称为分解模块(exploded module)格式。
  • 打包模块，生成模块化JAR文件
    • 模块化JAR文件类似于普通的JAR文件，但它还包含了module-info.class。
    • 与编译期间的模块目录名称不同，模块化JAR文件的名称并不重要。
  • 运行模块，支持分解模块格式和模块化JAR文件
    • 使用--module-path标志提供所运行的模块。
    • 以这两种方式中的任何一种启动都会使helloworld成为执行的根模块。
  • 模块路径，与类路径行为完全不同
    • 模块路径上的每个目录都可以包含零个或多个模块定义，其中模块定义可以是分解模块或模块化JAR文件。
    • 模块路径上的所有工件都有模块描述符(可能是在运行中合成，8.4节将会详细讨论相关内容)，解析器依赖此信息找到模块路径上的正确模块。
  • 链接模块，创建仅包含运行应用程序所需的模块的运行时映像
    • 通过使用一个名为jlink的新工具，可以创建仅包含运行应用程序所需的模块的运行时映像。
    • 运行上述命令的结果是生成一个新目录，包含了一个完全适合运行helloworld的Java运行时。

封装的限制

  • 前端需要与具体分析实施类型和模块相分离
    • 分析模块不应导出这些类型，以避免出现紧耦合。

第4章 服务

工厂模式

  • 工厂模式试图解决消费者与特定类的实例化进行解耦的问题。
  • 工厂模式只提供了部分解决方案，因为工厂模块在编译时仍然必须知道所有可用的实现
    • 每当出现一个新的分析模块时，工厂就需要依赖它来扩展getAnalyzer实现。

用于实现隐藏的服务

  • 使用服务，可以真正地共享公共接口，并将实现代码强封装到未导出的包中
    • 通过使用ServiceLoader API可在模块描述符和代码中表示服务。
  • 服务允许一个模块向其他模块提供实现，而不导出具体的实现类
    • 模块系统具有访问提供者模块的特殊权限，从而代表消费者实例化非导出的实现类。

服务生命周期

  • ServiceLoader工作“比较懒惰”，这意味着ServiceLoader::load调用不会立即实例化所有已知的提供者实现类
    • 每次调用ServiceLoader::load时，都会实例化一个新的ServiceLoader。当请求提供者类时，新的ServiceLoader会重新实例化它们。
    • 从现有的ServiceLoader实例请求服务将返回提供者类的缓存实例。

服务提供者方法

  • 可以通过两种方式创建服务实例，或者服务实现类必须具有公共的无参数构造函数，或者使用静态提供者方法
    • 提供者方法是一个名为provider的public static无参数方法，其返回类型是服务类型。
    • 当使用提供者方法时，provides…with子句指的是包含提供者方法的类(with之后)。

默认服务实现

  • 当一个服务类型具有默认实现时，为什么不直接从同一个模块中提供它呢？
    • 在JDK自身使用服务的方式中会经常看到这种模式。

服务实现的选择

  • 当存在多个提供者时，不一定要全部使用。可以根据某些特性筛选一种实现
    • 通常是消费者根据提供者的无属性决定使用哪种服务。
    • 如果存在多个提供者，但只对“最好的”实现感兴趣，该怎么做呢？Java模块系统不可能知道适合你的最佳实现。每个领域都有自己的需求。因此，将由自己根据服务类型配备方法，从而发现服务的功能，并根据这些方法进行决策。

具有服务绑定的模块解析

  • 服务的provides和uses子句为解析过程添加了另一个维度
    • requires子句表示模块之间严格的编译时关系，而服务绑定则发生在运行时。
  • 当解析一个带有uses子句的模块时，模块系统将在模块路径上找到给定服务类型的所有提供者模块，并将其添加到解析过程中
    • 这些提供者模块及其依赖项成为运行时模块图的一部分。

服务和链接

  • jlink从根模块easytext.cli开始执行模块解析，所有已解析的模块都包含在生成的映像中
    • 但是，该解析过程与上一节所讨论的启动时由模块系统完成的解析过程是不同的。在模块解析期间，jlink没有完成任何服务绑定，这意味着不会根据uses子句自动将服务提供者包含在映像中。
  • 默认情况下，jlink不包括服务提供者，因此在链接时需要完成一些额外的工作，尤其是当服务以传递的方式使用其他服务时
    • 这样做的好处是可以非常灵活地微调运行时映像的内容。不同的映像可以为不同类型的用户提供服务，只需重新配置需要包含的服务提供者即可。
第5章 模块化模式

确定模块边界

  • 模块边界应该源自系统的设计和意图
    • Parnas分区是一种模块化方法，通过使用Parnas分区，可以构建一个隐藏假设列表，该列表包含了系统中预期会发生变化或存在设计决策争议的地方，以及日后变化的概率。
  • 确定边界的标准决定了模块化工作的成功
    • 可理解性、可变性、可重用性、团队合作是设计模块时可以划分的几个参考标准。

精益化模块

  • 简化和最小化模块的公开导出部分是有益的
    • 一个简单而小巧的API比一个大而复杂的API更容易使用，模块用户不必考虑任何不必要的细节。
    • 最大限度地减少模块的公共部分可以减轻模块维护者的责任。
  • 精益化模块要尽可能独立，在可能的情况下避免依赖于其他模块
    • 如果只是想使用特定的模块，那么没有什么比看到系统中添加了大量的(可传递的)依赖项更让人沮丧的了。

API模块

  • 仔细研究模块的API是很有必要的，API设计已经成为构建合适模块的基本元素
    • 当对应用程序进行模块化时，构建应用程序模块的公共API是非常重要的。
  • API模块中应该包含什么
    • 接口包含了带有参数和结果类型的方法。
    • 接口是实现API提供者和消费者之间解耦的主要手段。
    • API模块可以包含比接口更多的内容，例如，希望API消费者扩展的(抽象)基类、枚举、注释等。
  • 隐式可读性
    • 隐式可读性允许存储库模块表达其自己导出的包不足以使用该模块。
    • 在设计API模块时，隐式可读性是使模块更易于使用的强大技术。
    • 依靠消费模块中的隐式可读性存在一个微妙的风险。
  • 带有默认实现的API模块
    • API的实现应该放在同一个模块还是单独的模块中？这是一个有趣的问题。
    • 组合的API /实现模块并不排除日后在单独模块中的替代实现。
    • 将API分离到自己的模块可以避免此类问题的出现。

聚合器模块

  • 使用隐式可读性来构建聚合器模块，其本质上是通过现有的库模块构建一个外观
    • 聚合器模块不包含代码，它只有一个模块描述符，为所有其他模块设置了隐式可读性。
  • 聚合器模块模式还有另一个有用的应用，即当一个整体模块发布后需要对其进行拆分时可以使用该模式
    • 假设需要对模块largelibrary进行进一步的模块化，但是largelibrary的用户正在使用其公共API，拆分需要以向后兼容的方式进行。
    • 新聚合器模块的消费者不会注意到其与所有代码在单个模块中之间有什么不同。

避免循环依赖

  • 拆分包是跨多个模块的单个包，当模块划分与现有的包边界不能保持一致时就会产生拆分包
    • Java中的包是非层次结构的。不管外表如何，splitpackage和splitpackage.internal是两个不相关却共享相同前缀的包。
    • 如果将module.one和module.two放在模块路径上，那么在启动JVM时会产生错误。Java模块系统不允许拆分包。
  • 当需要对现有JAR之间具有循环依赖关系的应用程序进行模块化时，该怎么办？或者说，如果从JAR中拆分包时会产生循环依赖，那么应该怎么办？
    • 一个显而易见的解决方案是将这些JAR合并成一个模块。
    • 通常，存在循环说明设计是有问题的，这意味着需要进行一些重新设计来打破这个循环。

可选的依赖关系

  • 如果一个模块在运行时不是绝对需要的，那么又该怎么办呢？
    • 目前许多框架都是按照以下方式工作的：向类路径中添加一个JAR文件(比如fastjsonlib.jar)，从而获得更多的功能。
    • Spring Framework是一个存在很多可选依赖关系的框架示例。
  • 服务提供了极大的灵活性，并且是解决应用程序中可选依赖关系的好方法
    • 但是，将服务绑定到ServiceLoader API可能是对现有代码一种侵入式更改。
    • 由于框架和库经常使用可选依赖关系，因此它们可能不希望强制用户使用服务API。

版本化模块

  • Java模块系统中的模块不能在module-info.java中声明一个版本
    • 不过，在创建模块化JAR时可以附加版本信息。
  • 语义版本控制规范了被广泛使用和理解的版本控制方案：MAJOR.MINOR.PATCH
    • 破坏性的更改(例如，更改了接口中的方法签名)会导致MAJOR版本部分发生变化。
    • 对向后兼容的公共API的更改(例如，在公共类上添加一个方法)则会改变版本字符串的MINOR部分。
    • 最后，当改变实现细节时PATCH部分会增加，所改变的实现细节可以是一个Bug修复或代码优化。

资源封装

  • 在默认情况下，模块中包内的资源被强制封装，这些资源只能在模块中使用
    • 许多工具和框架依赖于查找资源，而不管它们来自哪里。
    • 为了妥善处理这些情况并保持向后兼容性，在模块中封装资源的默认设置中增加了许多例外情况。
  • 从同一个模块中加载资源，无须为了加载资源而修改现有的代码
    • 资源通常通过Class API提供的资源加载方法进行加载。
    • Module API引入了从模块获取资源的新方法。
  • 跨模块加载资源时，只有顶级资源可以访问，包中的资源是被封装的
    • 类文件资源(以．class结尾)是例外；即使它们在包内，也不会被封装。
    • 所有其他资源可以被其他模块自由使用，但并不意味着应该这么做。
  • 使用ResourceBundle类时，只需添加一个模块就可以扩展应用程序中支持的语言环境
    • 它基于一个名为ResourceBundleProvider的新接口，包含一个带有签名ResourceBundle getBundle(String basename, Locale locale)的单一方法。
第6章 高级模块化模式

重温强封装性

  • 强封装性的优点和限制
    • 严格限制哪些是公开导出的API大有裨益。
    • 存在许多依靠访问应用程序的实现类来完成工作的库和框架。
  • 深度反射的问题和解决方案
    • 深度反射(deep reflection)的做法被许多库所使用。
    • 即使一个类型被导出，也并不意味着可以无条件地通过反射“闯入”这些类型的私有部分。
  • 开放式模块和包的概念和用法
    • 开放式模块提供了这些功能的组合。当开放一个模块时，所有类型都可以在运行时被其他模块深度反射。
    • 可以通过开放api包，从而使这个模块定义等同于开放式模块。
    • 有时需要对第三方模块进行深度反射。在某些情况下，有些库甚至想反射访问JDK平台模块的私有部分。此时添加open关键字并重新编译模块是不可能的。针对这些情况，为Java命令引入了一个命令行标志：--add-opens。
  • 依赖注入框架与开放式模块和包的关系
    • 在Java模块系统中，开放式模块和包是支持现有依赖注入框架的关键。
    • 取代反射：Java 9为应用程序中非公共类成员的基于反射的框架访问提供了一种替代方案：MethodHandles和VarHandles。

容器应用程序模式

  • 层和配置的概念
    • 层对于模块来说就像是类加载器对类那样——一种加载和实例化机制。
    • 已解析的模块图位于ModuleLayer内。层设置了一组连贯的模块。层本身可以引用父层，并形成一个非循环图。
  • 层中的类加载
    • 类加载器在运行时加载类。类加载器决定了可见性：如果某个类对于某个类加载器或其委托的其他类加载器可见，那么该类就可以加载。
    • 即使是跨层，类加载器之间的委托也必须遵守模块之间的可读性关系。
  • 插件体系结构
    • 插件通常独立于主机应用程序开发，主机应用程序和插件之间存在明确的界限。
    • 使用新的类加载器将每个插件模块加载到自己的层中还有另一个好处。通过这种方式来隔离插件，可以让插件依赖于相同模块的不同版本。

    • 另一种能够在运行时加载新代码的体系结构是应用程序容器体系结构。
    • 为了让事情变得更有趣，接下来将创建一个可以部署和取消部署应用程序的容器。
  • 解析容器中的平台模块
    • 在启动后加载新应用程序或插件时，可能会使用一些容器本身不需要的平台模块。
    • 前面介绍了层如何启用动态体系结构。它们允许在运行时构建和加载新的模块图，从而可能会改变包的开放性和可读性关系以适应容器。
第二部分 迁移

没有模块的迁移

  • 迁移到Java 9最好分两步进行，第一步是迁移现有代码以便在Java 9上构建和运行，而无须将代码迁移到模块
    • 升级到Java 9后就可以访问属于Java 9的其他功能了，想一想新的API、工具和性能改进。
  • 对于库的维护者来说，问题不在于Java 9的支持是否必要，而在于何时提供支持
    • 相比于迁移应用程序，将库迁移到Java 9和模块会引发完全不同的问题。

类路径已经“死”了？

  • 类路径在Java 9中仍然可用，并且工作方式与以前的版本大致相同
    • 如果忽略模块路径，而使用类路径来构建和运行应用程序，那么我们根本就没有在应用程序中使用新的模块功能。
    • 此时需要对现有代码进行最少的(如果有的话)更改。

库、强封装和JDK 9类路径

  • 将基于类路径的应用程序迁移到Java 9时可能遇到的一个问题是由平台模块中代码的强大封装所引起的
    • 许多库使用了平台中用Java 9封装的类，或者使用深度反射来窥探平台类的非公共部分。
    • 深度反射使用反射API来访问类的非公共元素。从模块中导出包不会使其非公共元素可用于反射。
  • 默认情况下，JDK 9不允许访问封装的包以及深度反射其他模块(包括平台模块)中的代码
    • 这样做的一个很好的理由是：平台内部类的滥用已经成为许多安全问题的源头，并且阻碍了API的发展。
    • 但是，在本章中仍然需要在模块化JDK之上处理基于类路径的应用程序。

编译和封装的API

  • JDK包含许多私有的内部API，这些API应该仅能被JDK所使用
    • 比如sun.*和jdk.internal.*包。
    • 作为应用程序开发人员，可能并不会直接使用这些类型。
  • 默认情况下，尽管代码使用封装包，但代码仍然可以在Java 9上成功运行
    • 你可能想知道为什么在访问封装类型时，javac和java之间存在区别。
    • 当无法编译相同的代码时，能够运行访问封装类型的代码又有什么意义呢？

删除的类型

  • 代码也可以使用目前已经完全删除的内部类型
    • 其中一个在Java 9中删除的内部类是sun.misc.BASE64Encoder。
    • 对于封装类型，可以通过使用命令行标志进行强制访问来解决此问题。
    • 但此时针对Base64Decoder示例无法这么做，因为该类不存在。

使用JAXB和其他Java EE API

  • JDK附带的某些Java EE技术(如JAXB)是与Java SE API一起提供的
    • 这些技术在Java 9中仍然存在，但是需要特别注意。
    • 它们主要包含在以下模块列表中：java.activation、java.corba、java.transaction、java.xml.bind、java.xml.ws、java.xml.ws.annotation。
  • 从JDK中删除Java EE技术有很好的理由
    • JDK中Java SE和Java EE之间的重叠一直是令人困惑的。
    • 模块系统不允许多个模块提供相同的包。

jdk.unsupported模块

  • JDK的一些内部类已经被证明更难以进行封装
    • 一般来说，使用sun.misc.Unsafe等类的机会是比较少的。
    • 由于性能原因，这些类中的一些被许多库广泛使用。
  • 考虑到这一点，达成了妥协
    • JDK团队研究了哪些JDK平台内部类是库使用最多的，哪些只能在JDK内部实现。
    • 这些类没有封装在Java 9中。

其他更改

  • JDK 9中的许多其他更改可能会破坏代码
    • JDK布局由于平台模块化，包含所有平台类的大rt.jar不再存在。
    • 版本字符串所有Java平台版本都以1.x为前缀开头的日子已经一去不复返了。
    • 扩展机制诸如授权标准覆盖机制(Endorsed Standard Override Mechanism)以及通过java.ext. dirs属性的扩展机制等功能已被删除。
第8章 迁移到模块

迁移到Java模块系统的策略

  • 专注于迁移自己的代码，而暂时保留库现有的工作方式
    • 如果一直等待整个生态系统向模块方向发展，那么可能要等很长时间。
    • 此外，还需要更新到这些库的新版本，从而可能引起一系列问题。
    • 也可以手动修补库，添加一个模块描述符并将它们转换为一个模块。
    • 显然，这需要完成大量工作，并且需要对库进行拆分(fork)，这使得未来的更新变得更加痛苦。

    • 虽然这样做是远远不够的，但却可以通过为模块创建一个简单的module-info.java开始迁移之旅。
  • 将jackson-databind-2.8.8.jar变成一个模块

混合类路径和模块路径

  • 为了使逐步迁移成为可能，可以混合使用类路径和模块路径
    • 但这不是一种理想的情况，因为只能部分受益于Java模块系统的优点。
    • 但是，“小步”迁移是非常有帮助的。

自动模块

  • Java模块系统提供了一个有用的功能来处理非模块的代码：自动模块
    • 只需将现有的JAR文件从类路径移动到模块路径，而不改变其内容，就可以创建一个自动模块。
    • 自动模块具有以下特征：不包含module-info.class；它有一个在META-INF/MANIFEST.MF中指定或者来自其文件名的模块名称；通过requires transitive请求所有其他已解析模块；导出所有包；读取路径(或者更准确地讲，读取前面所讨论的未命名模块)；它不能与其他模块拆分包。

开放式包

  • 使用Java Persistence API(JPA)就是这种情况的一个例子
    • 当使用JPA时，通常编程为标准化的API。而在运行时，会使用该API的实现，比如Hibernate或者EclipseLink。
    • API和实现在不同的模块中。最终，实现需要访问类。
  • 一个开放式包允许任何模块对其类型进行运行时访问(包括深度反射)，但编译时访问却是禁止的
    • 这避免了其他人在编译时意外地使用了实现代码，而框架可以在运行时毫无问题地施展它们的“魔力”。

开放式模块

  • 开放式模块提供了对其所有包的运行时访问，但并不会授予对包的编译时访问权限
    • 如果需要在编译时使用包，则必须将其导出。

破坏封装的VM参数

  • 在某些情况下，向模块添加exports或者opens并不是一个选项，可能是无法访问代码，或者只有在测试期间才需要访问
    • 在这些情况下，可以使用VM参数来设置更多的导出。

自动模块和类路径

  • 未命名模块的可读性只是一种在混合类路径/模块路径迁移方案中有助于自动模块的机制
    • 如果想要在代码中直接使用来自Jackson Core的类型(而不是来自自动模块)，那么必须将Jackson Core移动到模块路径中。

使用jdeps

  • jdeps是JDK附带的一个工具，用于分析代码并提供关于模块依赖关系的了解
    • 可以使用jdeps来优化迁移Jackson示例的过程。

动态加载代码

  • 在迁移到模块时可能需要特别小心的情况是使用反射来加载代码
    • 一个众所周知的例子是加载JDBC驱动程序。

拆分包

  • Java模块系统不允许拆分包
    • 当使用自动模块时，也会遇到拆分包。
    • 拆分包始终是一个错误，因为它们在类路径上不能可靠地工作。

使用Java 9在类路径上运行

    • 运行Main会导致java.lang.ClassNotFoundException:javax. xml.bind。
  • 使用--add-opens来消除警告

设置模块

  • 在module-info.java中针对任何编译时依赖项添加requires语句
    • 对于示例应用程序，可以根据直接的编译时依赖项提出以下requires语句列表：requires spring.context; requires spring.tx; requires javax.inject; requires hibernate.core; requires hibernate.jpa;。

    • 除了这些编译时依赖项之外，还有其他的编译时和运行时需求，可以使用--add-modules进行添加。

开放用于反射的包

重构到多个模块

第10章 库迁移

库迁移概述

  • 迁移库和迁移应用程序之间最大的区别在于库被许多应用程序使用
    • 这些应用程序可能运行在不同版本的Java上，所以库通常需要在各种Java版本上工作。
  • 库的迁移过程由以下步骤组成：
    • 确保库可以作为自动模块在Java 9上运行。
    • 使用Java 9编译器编译库(主要使用满足需求的最低Java版本)，而不使用新的Java 9功能。
    • 添加一个模块描述符，并将库转换为显式模块。
    • 重构库的结构，以便增加封装性，识别API，并尽可能分割成多个模块(可选)。
    • 开始使用库中的Java 9功能，同时保持向后兼容Java 9的早期版本。

模块化之前

  • 确保库可以与Java 9一起使用
    • 许多应用程序都是在类路径上使用库，甚至在Java 9上也是如此。
    • 库维护者还需要修改库，以便在应用程序中作为自动模块使用。
  • 在将一个库转变为一个模块(或模块集合)之前，应该像迁移应用程序一样采取相同的初始步骤
    • 确保在Java 9上运行库意味着它不应该使用JDK中的封装类型。
    • 如果使用这种类型，库用户可能会遇到警告或异常(如果它们使用推荐的--illegal-access = deny设置运行应用程序)。
    • 这就迫使他们使用--add-opens或--add-exports标志。但即使在库中使用这些标志，也不是一个良好的用户体验。
    • 通常，库只是应用程序中众多应用中的一个，因此，追踪所有正确的命令行标志对用户来说是非常痛苦的。
    • 最好是使用jdeps来查找库中封装API的使用，并将其更改为建议的替换内容。

选择库模块名称

  • 模块名称的最佳候选者是模块中所有包的最长公共前缀
    • 假设使用反向DNS包名称，顶级包名称就是一个自然的模块标识符。
    • 在Maven术语中，这通常意味着将组ID和工件ID组合为模块名称。
  • 数字在模块名称中是允许的
    • 虽然在模块名称中添加一个版本号(例如，com. mydomain.mylibrary2)可能会更有吸引力，但是不要这样做。
    • 版本控制是识别库的另一个独立问题。虽然创建模块化JAR时可以设置版本信息(如5.7节中所述)，但不应该是模块名称的一部分。

创建模块描述符

  • 关于创建模块描述符，有两个选择：从头创建一个或者使用jdeps根据当前的JAR生成一个
    • 不管使用哪种方法，最重要的是模块描述符拥有与之前在清单Automatic-Module-Name条目中所选择的模块名称相同的模块名称。
  • 当库包含包之外的类(在未命名的包中，俗称默认包)时，jdeps会产生一个错误
    • 模块中的所有类都必须是命名包的一部分。
    • 即使在模块出现之前，将类放在未命名的包中也是一种不好的做法——尤其是对于可重用的库而言。

使用模块描述符更新库

  • 可以用已编译的模块描述符来更新现有的JAR(使用较早的Java版本编译)
    • 将类文件提取到．/mylibrary。
    • 使用Java 9编译器将module-info.java编译到与所提取类相同的目录中。
    • 使用已编译的module-info.class更新现有的JAR文件。

针对较旧的Java版本

  • 可以使用两个JDK分别编译库源和模块描述符
    • 假设希望mylibrary在Java 7及更高版本上可用。
    • 实际上，这意味着库的源代码不能使用Java 7之后引入的任何语言功能，也不能使用Java 7之后添加的任何API。
  • 可以使用JDK 9包含的--release新标志来编译mylibrary示例
    • 这个新标志保证至少支持当前JDK的前三个主要版本。
    • 在JDK 9的情况下，这意味着可以针对JDK 6、7和8进行编译。

库模块依赖关系

  • 库由多个相关联的API组成时，库中的JAR之间存在依赖关系
    • 例如，Jackson由多个JAR组成，将这些JAR转换为模块是明智之举，可以保留当前的边界。
    • jdeps还可以为相关的JAR文件同时创建多个模块描述符。
  • 库使用了外部库时，库需要其他外部JAR
    • 如果这些外部库是显式的Java模块，那么答案很简单：在库的模块描述符中添加requires(transitive)子句就足够了。
    • 如果依赖项没有模块化又该怎么办呢？很多人会认为这没有问题，因为任何JAR都可以用作自动模块。

针对多个Java版本

  • 如果想要在不破坏向后兼容性的情况下在库实现中使用新的Java API，一种方法是有选择性地使用它们
    • 反射可用于定位新的平台API(如果可用的话)。
    • 另一种方法是，维护和发布针对不同Java版本的同一个库的多个版本，该方法同样没有吸引力。
  • 如果使用Java 9，则可以引入一个新功能：多版本JAR文件
    • 此功能允许将同一个类文件的不同版本打包到单个JAR中。
    • 相同类的这些不同版本可以针对不同的主要Java平台版本进行构建。
    • 在运行时，JVM会为当前环境加载最适合的类版本。
  • 多版本JAR也可以是模块化的
    • 只需在顶层添加模块描述符就可以了。
    • 如果在Java 9之前的运行时上使用JAR时，module-info.class将被忽略。
    • 也可以将模块描述符放在versions/9下。
第三部分 模块化开发工具

构建工具和IDE

  • 构建工具如Maven和Gradle可以处理各种问题，如类路径管理、依赖关系管理和构建工件等
    • 大多数开发人员都使用IDE，如Eclipse、IntelliJ IDEA或NetBeans，这些IDE提供了代码完成、错误突出显示、重构和代码导航等功能。
  • 随着Java模块系统的引入，类路径不再是控制哪些类型可用的唯一机制，工具现在也必须考虑使用模块路径
    • 可以混合使用显式模块、类路径和自动模块。

Apache Maven

  • Maven可以很容易地构建单个模块项目，并且可以处理Java模块系统的规则
    • 在编译期间使用模块路径。
    • 支持将显式模块和自动模块的混合体作为依赖项。
  • Maven中的模块名称(也称为Maven坐标)包含三个部分：groupId:-artifactId:version
    • groupId用于命名空间，在包含许多模块的项目中，groupId在逻辑上将这些模块组合在一起。
    • artifactId是模块的名称。
    • Maven模块被版本化。
  • 在Maven中，添加依赖项需要完成一个两步法：首先，需要将依赖项添加到表示该模块的Maven工件中，其次，在module-info.java中将依赖项作为requires语句添加
    • 如果没有在POM文件中添加依赖项，则编译器将在requires语句上失败，因为找不到该模块。
    • 但如果模块名称与Apache Maven group:-artifact:version坐标相同，则依赖项变成一个自动模块。

多模块项目

  • 在Java模块系统之前，通常使用Apache Maven创建多模块项目
    • 多模块项目中的每个模块都有自己的POM，这是一种XML格式的特定于Maven的构建描述符。
    • 在POM中配置了模块的依赖关系，包括对外部库的依赖以及对项目中其他模块的依赖。
  • 一个正确模块化的Apache Maven应用程序很容易迁移到Java模块系统
    • 从本质上来说，唯一需要做的是添加module-info.java文件。
    • 而作为回报，其将得到封装和更强大的运行时模型。

使用Apache Maven创建EasyText示例

  • 将EasyText目录结构更改为符合标准的Apache Maven目录结构
    • 每个模块都有自己的目录，包含模块源文件(包括moduleinfo.java)的src/main/java目录以及模块根目录下的pom.xml。
    • 其中要注意项目根目录下的pom.xml，这是一个父POM，可以用一个命令编译所有的模块。
  • 在父POM中包含对其子项目的引用，即实际的模块，其还将编译器插件配置为使用Java 9
    • modules部分并不是新的，与Java模块系统没有直接关系。
    • 模块本身也有自己的pom.xml文件，其中指定了模块的Apache Maven坐标(组名、工件名称和版本)及其依赖关系。

使用Apache Maven运行模块化的应用程序

  • Maven只是一个构建工具，在运行时没有任何作用
    • Maven构建了想要运行的工件，但是最后仍然需要配置Java运行时，以便运行正确的模块路径和类路径。
  • Maven有一个帮助完成该过程的exec插件
    • 只需要配置一个模块和主类来执行插件即可。

Gradle

  • 在编写本书时Gradle还没有提供官方的Java模块系统支持
    • 即使提供支持，其方式可能会类似于Maven。

IDE

  • IntelliJ、Eclipse和NetBeans等IDE也都支持Java模块系统
    • 支持Java模块系统的IDE的最重要特性是理解module-info.java文件中的requires和exports。
    • 这些关键字控制模块可用的类型，IDE应该使用它来完成语法，指出错误，并提供模块依赖关系的建议。
  • 在Eclipse中，每个项目都代表一个模块，假设它包含一个module-info.java
    • 一如既往，项目被分组在一个工作区中。
  • IntelliJ和NetBeans都已经有了自己的模块概念，现在可以直接映射到Java模块系统模块
    • 上述三个IDE也支持编辑module-info.java文件，包括模块名称的错误突出显示和语法完成。
    • 一些IDE甚至支持基于模块描述符的可视化模块图显示。
第12章 测试模块

黑盒测试

  • 黑盒测试是从外部测试模块，使用模块的公共API
    • 黑盒测试可以一次测试一个模块或多个模块。
  • 黑盒测试的优点是在自然环境下测试模块，缺点是只能对导出的部分进行直接测试
    • 黑盒测试的一个优点是可以在自然环境下测试模块。在测试模块时，就像其他模块在应用程序中使用它一样。
    • 以黑盒测试方式测试模块意味着只能对导出的部分进行直接测试，而无法对封装类进行测试，如VowelHelper类。同时，也不能访问SimpleSyllableCounter的任何非公共部分。

使用JUnit进行黑盒测试

  • JUnit是一个流行的单元测试框架，可以用于黑盒测试
    • 为了解决这个问题，需要重写测试代码，以便使用JUnit 4。
  • 使用JUnit进行黑盒测试需要将JUnit用作自动模块，并开放测试包
    • 一个开放式模块就足够了：open module easytext.syllablecounter.junit { requires easytext.syllablecounter; requires junit; }。
    • 为了解析测试模块，可以在启动测试运行器时定义一个--add-modules语句。

白盒测试

  • 白盒测试是从内部测试模块，需要访问封装的类和包私有的功能
    • 对VowelHelper进行单元测试意味着从黑盒测试切换到白盒测试。
  • 白盒测试可以通过使用类路径进行测试，也可以通过注入测试来修补模块
    • 使用类路径进行测试是最直接的，因为需要使用该方法的事情经常发生。
    • 通过使用称为模块修补(module patching)的功能，可以将新类添加到现有模块中。

测试工具

  • 大多数测试框架，如JUnit和TestNG，都使用类路径来运行测试
    • 即使代码包含模块描述符，大多数工具也都使用类路径来运行测试。
  • 如果代码依赖于模块描述符中使用新关键字的服务，那么就不会自动在类路径上工作
    • 此时，本章所介绍的黑盒测试场景更为合适。
第13章 使用自定义运行时映像进行缩减

创建自定义运行时映像的原因和优势

  • 易用性：jlink提供了应用程序和JVM的一个独立分发。
  • 减少占用空间：只有应用程序使用的模块才会链接到运行时映像。
  • 性能：由于链接时优化的代价过高或不可能，因此自定义运行时可能会更快地运行。
  • 安全性：在自定义运行时映像中只需最少的平台模块，因此攻击面更小。

静态链接和动态链接

  • 静态链接的一个优点是可以提前对整个应用程序进行优化
    • 这意味着从整个应用程序为出发点进行考虑，可以跨类和模块边界应用优化。
  • 链接与提前(AOT)编译不同。用jlink生成的运行时映像仍然由字节码组成，而不是本地代码
    • 整个程序优化的示例包括死代码消除(dead-code elimination)、常量合并(constant folding)和内联。

使用jlink创建自定义运行时映像

  • jlink工具位于JDK安装的bin目录中
    • 它不会默认添加到系统路径中，所以如果想要像本示例这样使用它，必须要先将其添加到路径中。
  • 可以提供多个以逗号分隔的根模块，而不是像此处使用多个--add-modules
    • 指定的模块路径显式包含了包含平台模块($ JAVA_HOME/jmods)的JDK目录。

查找正确的服务提供者模块

  • 可以使用--suggest-providers选项来帮助选择合适的服务提供者模块
    • 在下面所示的jlink调用中，只添加了easytext.gui模块，并询问Analyzer类型的提供者模块的建议。
    • 然后，可以通过添加--add-modules<module>来选择一个或多个提供者模块。

链接期间的模块解析

  • 平台模块需要显式地添加到模块路径
    • 另一个重要的例外涉及自动模块。当使用java或javac在模块路径中放置非模块化JAR时，其将被视为满足所有意图和目的的有效模块(请参见8.4节)。但是，jlink不会将模块路径上的非模块JAR识别为自动模块。
  • 在链接期间，使用反射模块时的注意事项仍然适用
    • 如果一个模块使用了反射并且没有在模块描述符中列出依赖项，那么解析器对此将不予考虑。

基于类路径应用程序的jlink

  • 还可以使用jlink创建Java平台的自定义映像，而不包括任何应用程序模块
    • 例如，可以运行jlink --module-path $JAVA_HOME/jmods --add-modules java.logging --output image并获得一个只包含java.logging(同时强制包含java.base)模块的映像。
  • 可以使用诸如jdeps之类的工具来查找运行该应用程序所需的最小平台模块集
    • 如果仅构建一个包含这些模块的映像，那么可以在此映像上启动基于类路径的应用程序，而不会出现问题。

压缩大小

  • jlink使用基于插件的方法来支持不同的优化
    • 本节以及下一节介绍的所有标志都由jlink插件处理。
  • 可以使用多个标志进一步减小映像的大小
    • 第一个标志是--strip-debug，它将删除本地调试符号，并从类中去除调试信息。
    • 也可以使用--compress = n标志压缩生成的映像。
    • 通过使用--vm = <vmtype>，可以选择不同类型的VM。
    • 最后一个优化涉及语言环境，通常，JDK附带许多语言环境，以适应不同的日期/时间格式、货币和其他区域敏感信息。

提升性能

  • 很多实验性插件在链接时生成代码来提高启动性能
    • 默认启用的一种优化是预先创建平台模块描述符缓存。
    • 另外，其他插件在链接时执行了字节码重写，从而提升了运行时性能。
  • jlink可以优化来自任何模块的代码，无论是应用程序模块还是所使用的库模块或是平台模块
    • 不过，因为jlink插件允许任意的字节码重写，所以它们不仅仅只是用来增强性能。

跨目标运行时映像

  • jlink可以为不同的平台创建映像，其过程非常简单
    • 不要将当前运行jlink的JDK的平台模块添加到模块路径，而是指向具体的操作系统和体系结构的平台模块。
  • 使用jlink构建的运行系统映像不会自动更新
    • 当发布新的Java版本时，需要构建更新的运行时映像。
第14章 模块化的未来

Java模块系统的优势与应用

  • 建议针对新代码采用模块，为创建可维护系统奠定坚实基础
    • 在一开始就应用强封装并管理显式依赖关系。
  • Java模块鼓励在模块化开发中采用经过实践检验切实可行的最佳实践
    • 使用jlink创建自定义运行时映像。

OSGi与Java模块系统的比较

  • OSGi通过在OSGi容器中运行bundle提供运行时模块化
    • 通过巧妙地安排类加载器来控制类的可见性，从而实现了bundle之间的隔离。
  • OSGi和Java模块系统之间存在显著差异
    • 包依赖关系：OSGi bundle表示了对包的依赖关系，而不是对其他bundle的依赖关系。
    • 版本控制：与Java中的模块不同，OSGi中bundle和包都有版本。
    • 动态加载：bundle可以在OSGi运行时中加载、卸载、启动和停止。
    • 动态服务：OSGi还定义了一个带有中央服务注册表的服务机制。
