核心追问（来自深读）

模块系统解决的到底是“打包”问题，还是“可见性”问题？

是可见性与可解析性，不是打包。classpath 是扁平全通的：任何 jar 里的 public 类对所有代码可见，缺一个 jar 只在运行到那行时抛 NoClassDefFoundError。JPMS 用 module-info.java 把四件事写成编译期契约：requires（我依赖谁）、exports（我对外暴露哪些包）、opens（哪些包允许反射）、uses/provides（我消费/提供什么服务）。于是“缺依赖”从运行时异常前移到启动期的模块解析失败。作者用“可靠配置”概括这一点。这也划出了它与 OSGi 的分野：OSGi 面向运行时动态装卸，JPMS 面向启动时静态可验证——用灵活性换可推理性。

第 5、6 章的“模块化模式”，为什么说比 API 设计更靠前？

因为边界定错之后，所有的 exports 都只是补丁。书里把模式分成结构性与演化性两类：结构性的是 API 模块与实现模块分离、聚合模块只做 re-export、可选依赖用 requires static；演化性的是如何在不破坏兼容的前提下新增实现、如何用服务解耦。判断标准很硬：如果实现类必须导出才能被使用，说明抽象没做够；如果为了测试要 opens 整个包，说明测试边界和模块边界打架。换句话说，模块化不是“加一个 module-info”，而是先回答“谁有权看到什么”，这一步错了，工具帮不了你。

迁移章节为什么坚持“自下而上”，而不是一次性切到模块路径？

因为未命名模块与自动模块可以共存，这给了渐进路径。自下而上指先模块化依赖树底部（没有第三方依赖的库），再逐层向上；尚未模块化的第三方库先留在 classpath，或作为自动模块——模块名由 jar 文件名推导，不稳定是主要风险。第 9 章的 Spring/Hibernate 案例说明了真正的难点：这类框架重度依赖反射与类路径扫描，必须先 opens 再谈 exports，否则编译通过、启动就炸。迁移的成本几乎全在运行时行为，不在编译期，这正是不能“一次到位”的原因。

这本书三部分各自解决什么问题？

第一部分讲“怎么用”：从模块化 JDK 本身开始，教你写自己的模块，再用服务解耦，最后讨论模块化模式与高级模式，目标是可维护、可扩展。第二部分讲“怎么搬”：把现有代码迁进模块、处理尚未模块化的第三方库，并专设一章给库作者讲如何添加模块支持。第三部分讲“怎么配合工具”：IDE 与构建工具的现状、如何测试模块、如何用 jlink 生成自定义运行时映像，以及对模块化未来的判断。三段合起来是一次完整的工程落地路径。

services 为什么被当作解耦的核心机制？

因为 uses/provides 让调用方只依赖接口，实现在启动时由 module path 上的提供者绑定，ServiceLoader 负责发现。好处是调用方编译期完全不需要知道实现模块；代价是编译期保证变弱——提供者缺失只在运行时报错，除非显式校验。这和 Spring 的容器装配是两种哲学：JPMS 是平台级契约，Spring 是容器级装配。前者适合“框架与实现分离”的库设计，后者适合应用内的高度可配置。两者并不互斥，但混用时要清楚谁负责生命周期。

jlink 裁剪运行时，边界在哪里？

jlink 只裁剪 JDK 模块与你自己的模块闭包，无法裁掉第三方非模块化 jar 内部未使用的类——自动模块会被整体纳入。所以镜像大小取决于模块化程度：模块化越彻底，闭包越精确，收益越大。推论是：对一个依赖几十个非模块化 jar 的应用，jlink 的缩减率会远低于宣传值。这也解释了书中为什么把“库模块化”单独成一章：没有生态的模块化，jlink 只是半个工具。

用更高维度的知识看这本书

把 JPMS 放回历史：它是 2000 年代以来模块化争论的收束——OSGi 的动态装卸、Maven 的“依赖即类路径”、JSR 277/294 的反复摇摆。最终方案选择了编译期加启动期的静态模型，主动放弃热部署，换取可推理性。与 .NET 的 assembly、Rust 的 crate 相比，JPMS 最特殊的一点是把“反射可访问性”也写进契约（opens）——这既是它对 JVM 生态的妥协，也是对 Java 反射传统的正式承认。

争议在于落地效果。JPMS 并没有成为应用层的主流模块化方案，实际收益集中在 JDK 自身、库的强封装与 jlink 裁剪。原因有三：Spring 等框架依赖类路径扫描，opens 把收益抵消掉大半；Maven/Gradle 的依赖解析已经解决了大部分可见性问题；模块路径与类路径混用还带来“分裂包”等新故障。所以这本书的真正价值，是理解 JDK 的设计意图与迁移摩擦的来源，而不是当作应用架构指南来读。

阅读时要验证的问题

  • 核对“可靠配置”是否真能把缺依赖前移：自动模块名不稳定、滥用 --add-opens 都会让保证失效，需实测启动行为。
  • 检查第 5 章的模式是否给出可判定准则（导出即承诺），否则“模式”容易退化为命名习惯，无法评审。
  • 验证 jlink 的实际收益：对含大量非模块化依赖的项目，裁剪率可能远低于预期，应实测镜像体积与启动时间。
  • 核对 Spring/Hibernate 案例是否回答了“框架不模块化时应用能否模块化”，这决定迁移策略是否可行。

当年与今天 · 初步对照

书对应 Java 9（2017）。今天 Java 17/21 已是主流，强封装默认开启，JDK 内部 API 不再默认开放，书中“用 --add-opens 过渡”的权宜之计，如今更像技术债。同时 GraalVM native-image 从另一条路解决“运行时太大、启动太慢”，jlink 的独占地位被削弱。读第 13 章时要带着这个变化：它讲的收益仍然成立，但不再是唯一解。

新变量还有虚拟线程（Java 21）与容器化。虚拟线程改变了“一个请求一个线程”的栈模型，模块边界与线程边界不再天然对应；容器让“镜像小”由基础镜像与分层缓存解决，jlink 的价值从“体积”转向“攻击面与启动确定性”。因此第 14 章“模块化的未来”值得重读：它讨论的不是语法，而是 Java 生态是否愿意为可推理性付出耦合成本。
