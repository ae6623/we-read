7第1章 缓存为王›

4 个小节 · 15 句热门划线

1.1 什么是缓存？

  • 缓存：存储在计算机上的一个原始数据复制集，以便于访问。
  • CPU是有多级缓存的，有时候也称为几级流水
  • 编程的时候，接触到的都是虚拟地址而不是真实的物理地址，这是虚拟内存的主要功能之一

1.2 为什么使用缓存？

  • 如果说音乐是时间的艺术，那么，缓存就是软件系统中关于时间的艺术。“缓存为王”本质上是系统性能为王，对用户而言就是用户体验为王。
  • 缓存离客户端更近，从缓存请求内容比从源服务器所用时间更少，呈现速度更快，系统就显得更灵敏

1.5 网络中的缓存

  • 反向代理与正向代理相反，对于客户端而言代理服务器就像是源服务器，并且客户端不需要进行设置。客户端向反向代理发送普通请求，接着反向代理将判断向何处转发请求，并将从源服务器获得的内容返回给客户端。
  • 如果这些反向代理服务器能够做到和用户来自同一个网络，那么用户访问反向代理服务器，就会得到很高质量的响应速度，所以可以将这样的反向代理缓存称为边缘缓存。
  • 常用的Web代理分为正向代理、反向代理和透明代理
  • 边缘缓存中典型的商业化服务就是CDN了
  • 而是直接将缓存的数据传送给用户的浏览器，这样就能显著提高浏览速度和效率

1.6 服务端缓存

  • 如果当前已经缓存的表未达到table_cache数目，则会将新表添加进来；若已经达到此值，MySQL将根据缓存表的最后查询时间、查询率等规则释放之前的缓存。
  • 在CPU缓存淘汰和虚拟内存系统中效果很好。然而在直接应用与代理缓存中效果欠佳，因为Web访问的时间局部性常常变化很大。
  • 此处常用的负载均衡算法是轮询或者一致性哈希，轮询可以使服务器的请求更加均衡，而一致性哈希可以提升Nginx应用的缓存命中率。
  • 所有的Redis节点通过PING-PONG机制彼此互联，内部使用二进制协议优化传输速度和带宽。节点故障是通过集群中超过半数的节点检测失效时才会生效。
  • 在Java语言中，缓存框架更多，例如Ehcache, Cacheonix, Voldemort, JBoss Cache, OSCache等等

2.2 分布式系统概念

  • 所谓幂等性就是调用1次和调用N次要返回一样的结果。
  • 和并发的区别：并发和并行是即相似又有区别的两个概念，并行是指两个或者多个事件在同一时刻发生；而并发是指两个或多个事件在同一时间间隔内发生。
  • 我们可以看看DefaultMethodRetryHandler（commons-httpclient-3.0）的代码，默认retry次数为3
  • 设计容错系统的一个方案是，任何消息只有收到对方回复才可以认为发送成功。
  • 这种方式我们称之为并发（Concurrent）。
  • 当系统有一个以上的CPU时，则线程的操作有可能非并发。当一个CPU执行一个线程时，另一个CPU可以执行另一个线程，两个线程互不抢占CPU资源，可以同时进行，这种方式我们称之为并行（Parallel）。
  • 分拆锁有时候可以被扩展，分成若干加锁块的集合，并且它们归属于相互独立的对象，这样的情况就是分离锁。

2.3 分布式系统理论

  • 如果不要求P（不允许分区），则C（强一致性）和A（可用性）是可以保证的。但其实分区不是你想不想的问题，而是始终会存在，因此CA的系统更多的是允许分区后各子系统依然保持CA。
  • Paxos协议是一个解决分布式系统中，多个节点之间就某个值（提案）达成一致（决议）的通信协议。它能够处理在少数节点离线的情况下，剩余的多数节点仍然能够达成一致。
  • 脑裂（split-brain），指在一个高可用（HA）系统中，当联系着的两个节点断开联系时，本来为一个整体的系统，分裂为两个独立节点，这时两个节点开始争抢共享资源，结果会导致系统混乱，数据损坏。
  • 引擎给每张表都增加2个字段，分别叫作create version和delete version。
  • 分区容忍性（P）：以实际效果而言，分区相当于对通信的时限要求
  • 2PC最大的不足是提交协议是阻塞型协议
  • 可感知其影响的情况下，就要预备一种策略去探知分区并显式处理其影响。这样的策略应分为三个步骤：探知分区发生，进入显式的分区模式以限制某些操作，启动恢复过程以恢复数据一致性并补偿分区期间发生的错误。

2.4 分布式系统设计策略

  • 集群模式是指有多个节点在运行，同时可以通过主控节点分担服务请求，比如zookeeper。集群模式要特别解决主控节点本身的高可用问题。
  • 系统高可用性的常用设计模式包括三种：主备(Master-SLave)、互备(Active-Active)和集群(Cluster)模式。
  • TFS涉及到NameServer、DataServer两类节点。NameServer存放了元数据，而具体的业务数据存放于DataServer。

2.5 分布式系统设计实践

  • Flicker的方案是启用两台数据库服务器来生成ID，通过区分auto_increment的起始值和步长来生成奇偶数的ID。
  • 拆分数据库也存在扩容的问题，解决方法是先预设足够大的逻辑库，比如100个库，随着物理负载的增加，把对应的逻辑库迁移到新增的物理库上即可，对于应用透明，相当于在应用和物理数据库之间增加了一层映射关系。
  • 一致性哈希的优点在于可以任意动态添加、删除节点，每次添加、删除一个节点仅影响一致性哈希环上相邻的节点

核心追问（来自深读）

作者为什么说“解决雪崩问题的最好办法是不发生雪崩”？它针对的是缓存的什么特性？

这句话出现在推荐序与前言里，是全书的方法论基调：缓存一旦被击穿、失效或集中过期，海量请求会瞬间砸向后端数据库，造成连锁瘫痪（雪崩）。作者认为与其事后补救，不如在设计上消除触发条件——比如错开过期时间、预热热点、限流与降级。从应用程序视角看，开发者不必人人会造缓存组件，但必须具备“正确使用它”的能力，因为不同数量级的请求产生的结果天壤之别，使用不当比不用更危险。

分布式缓存里“幂等性”为什么被反复强调，它和缓存更新有什么关系？

书里把幂等性定义为“调用 1 次和调用 N 次返回一样的结果”。在分布式缓存与缓存一致性场景里，网络重试、消息重放、并发写入都很常见，如果操作不具备幂等性，重试就会把数据改坏或重复写入。例如关系（relation）的存储方案里，用 DB 事务插入带唯一变更 ID/版本号的记录，再在缓存写入时带上同一版本号并回删 DB 记录——正是用版本号把“更新缓存”变成可重复、可校验的幂等操作，从而避免并发下的状态错乱。

从架构演进看，缓存为什么“为王”？它分布在系统的哪几层？

书的第一章就叫“缓存为王”，提要也写道“缓存就是软件系统中关于时间的艺术”。因为性能瓶颈往往不在算力而在等待，而“用空间换时间”的缓存能把高频访问从慢路径（磁盘/网络/计算）挪到快路径。作者沿着网站架构发展，把缓存拆成客户端缓存、网络中的缓存、服务端缓存三层：浏览器与 CDN 边缘缓存离用户最近，反向代理缓存（如把请求转发到源站前先做判断）居中，服务端本地缓存与分布式缓存（如 Memcached）兜底。

这本书的定位和读者价值是什么？

它源于作者多年对缓存技术的热情与一线案例积累：既关注开源框架发展，也记录工作中所遇所见的雪崩、击穿等惨痛故事。书中明确区分了“开发一套组件”与“正确使用它”——后者才是大多数程序员真正需要的能力。内容从缓存概念、网站架构演进中的缓存角色，讲到客户端/网络/服务端缓存，再到分布式系统理论（CAP、Paxos 等）与典型问题解析。适合想搞清“缓存为什么快、又会怎么害死你”的工程师。

书里是怎么把“分布式系统理论”和缓存实践连起来的？

划线里出现了几组关键概念：一是 CAP——若不要求 P（分区），C 和 A 才可兼顾，但分区其实始终存在，所以“CA 系统”多指分区后各子系统仍保 CA；二是 Paxos，用于在少数节点离线时让多数节点仍达成一致；三是并发与并行之别（并行是同一时刻、并发是同一时间间隔）。这些理论支撑了缓存集群的一致性、可用性与容错设计，说明缓存不是孤立技巧，而是分布式系统的缩影。

“巨热 key”问题书里给了什么思路？

划线提到一个具体手法：把巨热数据的 key 发布到所有服务器上，每台给该 key 一个别名（如 get key:xxx => get key:xxx#N），从而把单点极热访问分散到多机，避免某台缓存被压垮。这背后是“复制热点 + 别名分流”的思想，与一致性哈希解决数据倾斜是一体两面。它提醒我们：缓存性能瓶颈常常不是容量，而是单 key 的访问集中度，治理要针对“分布”而非“总量”。

用更高维度的知识看这本书

把本书放回工程脉络：缓存思想可追溯到 1960 年代 CPU 多级缓存与虚拟内存，互联网时代它被放大成“系统性能的总开关”。作者引易宝 CTO 陈斌“解决雪崩的最好办法是不发生雪崩”，与后来 Google SRE 的“错误预算、避免级联故障”理念同源。CAP 与 Paxos 则由 Eric Brewer、Leslie Lamport 在 2000 年前后提出，是分布式缓存无法绕开的理论地基。

需要补的外部视角是：今天的缓存已不只是 Memcached/Redis 这类组件，而延伸到浏览器、CDN、边缘计算与数据库内置缓冲（如 MySQL 的 table_cache，书里也提到）。同时“缓存一致性”在微服务下更棘手，衍生出 Cache-Aside、Read-Through、Write-Behind 等模式与多级缓存框架。读本书应把具体工具当例子，把“时空权衡、热点治理、一致性代价”当主干。

阅读时要验证的问题

  • “错开过期、预热热点”是治本方向，但具体阈值与容量需结合业务 QPS 与后端承压实测，勿照搬书中案例数字。
  • CAP 中“分区始终存在”是经验性前提，实际少数网络分区可极短，是否牺牲 C 或 A 取决于业务，须自行判断。
  • 巨热 key 的别名分流会增加一致性与失效复杂度，落地前需评估别名刷新与失效的传播代价。
  • LRU 在 Web 代理缓存中效果欠佳（书里指出时间局部性多变），现代多用 LRU-K、ARC、W-TinyLFU 等变体，引用时应更新。

当年与今天 · 初步对照

本书成书时，Memcached、Redis 之争与自建缓存正当主流；今天 Redis 已成事实标准，并叠加了持久化、集群、Lua、Stream 等能力，云厂商更是把缓存做成了托管服务。当年需要手工设计的“预热、错峰、限流”，如今多被平台能力吸收。但“雪崩/击穿/穿透”这三类经典问题并未消失，只是从运维事故变成了架构面试的必答题。

对当下读者的迁移价值在于：缓存的本质是“用时间维度换空间与性能”，这个权衡在任何新硬件（如 NVM、GPU 显存缓存）与新架构（如 Serverless 冷启动）里都成立。读这本书，学的是“如何敬畏热点、尊重一致性边界”，而不是某个具体客户端的命令。记住那句被反复划线的忠告——最好的修复，是让它根本不发生。
