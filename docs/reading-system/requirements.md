# 读书系统需求文档

版本：v0.2（合并雨的两轮补充）
状态：待用户确认开放问题后进入第一期开发

---

## 1. 背景与目标

### 1.1 现状与痛点

现在的读书流程由共享仓库、群聊和 agent2agent 共同推进。书目状态、活动锁和续读点写在 `book-registry.json`，成员花名册写在 `agent-roster.json`，每日协作日志写在 `agent-communication/`。写入靠 Git 提交和 PR，由管理员合入。

主要问题如下：

- 群聊和 agent2agent 来回确认，一场活动常要几轮消息，拉齐一个团队并推进产出需要约一天。
- 每次行动前都要核对 main 的最新状态，依赖人工判断。
- 浏览器登录态经常掉线，需要用户手动登录，而且系统不能及时发现。
- GitHub 写入依赖各会话的连接器是否启用，子任务常停在提交前。
- Gemini 额度用完要人工换模型；定时任务数量有上限。
- 一天的产出要靠人工汇总日报和笔记链接。

### 1.2 目标

- **系统是任务与状态的真相源。** 任务、排班、锁、场次、产出和审核结论都写入系统数据库，由系统判定谁可以做什么。
- **GitHub 降为发布与审计归档层。** 只接收系统导出的内容，不接收读书员的直接写入。理由：Git 适合审计和公开发布，但不适合做高频状态推进。
- **群聊只用于用户可见的通知与人工决策，不再用于推进任务。** 理由：群聊消息不可靠、难以追溯，推进任务应由系统完成。
- **读书员只读取分派给自己的任务，干完后通过系统回写。** 理由：读书员无需理解全局流程，减少来回确认。
- **后台 job 自动推进。** 排班核对、提醒、催办、日报和异常通知由系统定时执行，取代人工盯盘。

### 1.3 不做什么

- 不自动续读、不自动补跑过期场次。理由：过期场次的状态不可靠，补跑可能与真实浏览器状态冲突。
- 不自动接管未确认停止的旧运行。只能由人工裁定。
- 不代认领书目。书目只能由管理员下发或由读书员按规则领取。
- 管理员不阅读书籍正文，不替代读书员的阅读。
- 不借用他人的登录会话，不通过拼接 URL 绕过登录。
- 第一期不做多租户 SaaS，不做面向公众的实时看板。

## 2. 角色与权限

| 角色 | 主要职责 | 读任务 | 写回结果 | 登记/锁 | 审核 | 维护规范/排班/记忆 | 查看数据 | 登录浏览器 |
|---|---|---|---|---|---|---|---|---|
| 管理员 | 维护角色、任务、排班、规范、记忆；下发任务；审核合入 | 是 | 否（不写正文产出） | 管理排班，不占锁 | 是（不审自己下发的产出） | 是（记忆改动需审核） | 是 | 否 |
| 读书员（微信读书 / 轻游记 / 读书时长专员 / Windows 本地 PDF） | 只读领到的任务，执行，回写结果 | 仅自己的任务 | 是（仅自己的场次） | 是（仅自己的场次） | 否 | 否（记忆改动需提交审核） | 仅自己的数据 | 仅在用户完成登录后使用 |
| 用户（雨） | 审批排班与重大决策；查看数据；处理登录与异常 | 是 | 否 | 否 | 可抽查 | 审批 | 是 | 手动登录共享浏览器 |
| 后台 job | 定时检查、催办、生成日报、发通知 | 是 | 仅系统状态字段 | 仅超时标记，不获取锁 | 否 | 否 | 是（只读汇总） | 否 |

理由：读书员与管理员分离，避免一个角色既执行又审核；后台 job 不获取资源锁，避免它与读书员争抢浏览器。

## 3. 身份与认证

- **每个读书员使用独立凭据。** 系统为每个 agent 颁发一个独立的服务凭据，可单独撤销。理由：避免借用他人会话，撤销一个读书员不影响其他角色。
- **凭据只存引用，不入库。** 凭据值保存在密钥存储中，系统库只保存引用名、状态、颁发时间和撤销时间。理由：数据库可能被导出或备份，值不应出现在其中。
- **不依赖会话连接器。** 读书员通过系统 API 读写状态，不再依赖 GitHub 连接器是否启用。理由：这是子任务停在提交前的根源，移除后可以消除该隐性前提。
- **agent 使用机器键标识。** 机器键保持不变，公开标题仍用“AI读书”。
- **凭据轮换。** 每次轮换生成新引用，旧引用在一个交接窗口后失效。

## 4. 核心对象（数据模型）

### 4.1 对象清单

| 对象 | 关键字段 | 说明 |
|---|---|---|
| Agent / 角色 | 机器键、角色类型、资源类别、凭据引用、状态（启用/停用/已撤销）、版本号 | 读书员与管理员；花名册的系统版本 |
| 书目 | 书目编号、系列、标题（公开）、机器键、来源文件引用、状态、续读点、版本号 | 对应 `book-registry.json` 的一条记录 |
| 任务 | 任务号、书目、指派角色、类型（读/AI问答/笔记/核验）、状态、截止时间、版本号 | 管理员下发，读书员只读分派给自己的任务 |
| 排班槽位 | 槽位号、角色、资源类别、开始/结束时间、状态 | 由管理员统一制定；有禁读时段约束 |
| 资源 | 资源键（如共享浏览器、时长专员浏览器、本地 PDF）、持有场次、获取时间、版本号 | 锁的载体 |
| 场次 | 场次号、槽位、书目、角色、状态、开始/结束时间、超时标记、停止原因 | 一次实际开读 |
| 运行记录 | 场次号、步骤、结果摘要、错误、时长 | 执行过程的可追溯记录 |
| 笔记与产出 | 书目、章节、类型、作者角色、标签（亲读/AI问答/推断）、核验状态、存储位置、版本号 | 笔记与产物的索引；正文存文件 |
| AI 问答记录 | 提示词、模型、调用时间、来源引用、原始回复引用、核验状态、核验结果 | 见第 8 节 |
| 规范版本 | 规范编号、版本号、内容引用、生效时间、批准人 | 只追加，不覆盖 |
| 记忆条目 | 角色、内容、版本号、来源、审核结论 | 改动需审核 |
| 日报 | 日期、汇总内容引用、生成时间、发布状态 | 每日一条 |
| 审核记录 | 对象类型、对象版本、审核人、时间、结论、备注 | 不可修改，见第 14 节 |
| 通知 | 事件键、接收渠道、内容、发送时间、送达状态、确认状态 | 见第 9 节 |
| 审计日志 | 操作者、动作、对象、前后版本、时间 | 只追加 |

### 4.2 状态流转

**任务状态**：待下发 → 已下发 → 已登记 → 执行中 → 待回写 → 待审核 → 已合入。另有异常分支：阻塞（需人工）、已取消、已过期。

**场次状态**：已排班 → 待登记 → 已登记 → 开读中 → 收尾中 → 已回写 → 已合入。异常分支：阻塞（登录失效，停在登记前）、超时待裁定、已停止（人工确认）、漏跑（不补跑）。

**资源锁状态**：空闲 → 占用（持有人为某场次） → 释放中 → 空闲。超时后转为“占用-待裁定”，不自动释放。

**关键规则**：只能按上述箭头转换，非法转换直接拒绝并记录审计日志。理由：状态机是防止并发混乱的最后一道防线。

## 5. 任务下发与回写流程

| 步骤 | 执行方 | 动作 | 系统检查 | 是否仍需人工 |
|---|---|---|---|---|
| 1 | 管理员 | 在系统中下发任务，指定书目与读书员 | 书目未被其他活动场次占用 | 否 |
| 2 | 用户 | 审批当日排班与重大变更 | 排班不落在禁读时段 | 是（审批） |
| 3 | 后台 job | 开始前 10 分钟检查登录态与任务状态 | 登录态健康检查 | 视结果 |
| 4 | 读书员 | 读取分派给自己的任务 | 凭据有效，任务属于本人 | 否 |
| 5 | 读书员 | 登记场次并申请资源锁 | 原子获取锁，同一书目唯一活动场次 | 否 |
| 6 | 读书员 | 执行阅读、笔记或 AI 问答 | 运行中定期心跳 | 微信读书登录失效时需用户手动登录 |
| 7 | 读书员 | 回写结果与续读点 | 版本号校验，冲突拒绝 | 否 |
| 8 | 读书员 | 释放资源锁 | 仅持有人凭围栏令牌释放 | 否 |
| 9 | 管理员 | 审核产出 | 审核结论写入审核记录 | 否 |
| 10 | 系统 | 合入系统状态，生成导出包 | 脱敏检查通过才允许导出 | 否 |
| 11 | 后台 job | 导出到 GitHub 做发布与归档（经 PR 或自动发布，见开放问题） | 导出内容不含凭据、UID、群 ID、私人路径 | 否 |
| 12 | 后台 job | 通知用户完成或异常 | 通知去重，静默时段排队 | 否 |

**仍需人工的步骤**：用户手动登录共享浏览器（微信读书、轻游记）；审批排班；裁定超时场次；抽查审核结论。

## 6. 资源锁与并发

### 6.1 资源冲突判定

- 共享浏览器资源（微信读书与轻游记共用）：同一时间只能有一个场次持有。
- 时长专员使用独立浏览器资源，与共享浏览器互不冲突。
- 本地 PDF 使用独立资源，不占浏览器，与浏览器资源互不冲突。
- 同一书目同一时间只能有一个活动场次，由数据库唯一约束保证。

理由：资源按“持有者”判定，而不是按角色名判定，便于新增角色。

### 6.2 原子性

- **获取锁**：单条条件更新（资源空闲时才写入持有人并递增版本号），返回成功才算获得。理由：避免两个读书员同时判定为空闲。
- **释放锁**：必须携带获取时的围栏令牌，令牌不匹配则拒绝。理由：防止旧场次误释放新场次的锁。
- **同一书目唯一活动场次**：数据库唯一索引，覆盖状态为活动的场次。

### 6.3 乐观锁

- 书目、任务、场次、记忆条目等可变对象都有版本号。
- 回写时必须带上读取时的版本号；版本不一致则返回冲突，要求读书员重新读取后再写。
- 冲突不自动合并，避免覆盖他人结果。

### 6.4 错峰

- 轻游记在整点开始，微信读书在半点开始，读书时长专员在 00:10 开始。
- 禁读时段为 02:00–06:00，系统拒绝在该时段登记场次。
- 若前一场次仍持有共享浏览器，后一场次不排队等待，直接记为“资源冲突”并通知，不补跑。理由：沿用既有“过期场次不补跑”规则。

### 6.5 超时与停止

- 每个场次有最长时长（按槽位时长加宽限时间，具体数值待定）。
- 超时后场次转为“超时待裁定”，锁保持占用，不释放。
- 人工裁定只有两种：确认已停止（释放锁并记录原因），或确认仍在运行（延长并记录批准人）。
- 系统不得自动接管、补跑或续读旧运行。理由：未确认停止的浏览器状态可能仍在变化，自动接管会导致数据错乱。

## 7. 调度与状态机规则

- 排班由管理员统一制定，用户审批后生效。
- 系统自带调度器执行所有定时任务，不再使用 Cue 定时任务，因此不受数量上限约束。
- 开始和结束都必须在系统中留下记录（替代既有的报备 PR）。
- 漏跑记录：场次结束时仍处于“待登记”或“已排班”，标记为漏跑，不补跑。
- 任何状态转换都写审计日志。

## 8. 浏览器登录态托管（一等风险）

浏览器登录态是系统最容易失效、也最需要人工介入的环节，因此单独列为一等风险。

- **健康检查**：每场次开始前 10 分钟执行一次；另外每 30 分钟执行一次轻量检查。
- **过期告警**：检查失败时，场次停在“登记前”，锁不被获取，并通知用户。理由：在登录失效状态下开读只会产生空数据或错误数据。
- **人工重新登录**：由用户在共享浏览器中自行登录，系统在登录后再次检查，通过后场次才能进入登记。
- **禁止事项**：不借用其他读书员的登录会话，不拼接 URL 绕过登录，不自动填写或保存他人的账号密码。
- **记录**：每次失效记录时间、影响的场次和恢复时间，用于统计失效次数。

## 9. 后台 job 与通知

### 9.1 job 清单

| job | 触发时间 | 规则 | 失败或异常时 |
|---|---|---|---|
| 排班核对 | 每小时整点 | 对比排班与场次状态，发现缺失、重复或时段错误 | 通知管理员，并记录异常 |
| 登录态检查 | 每场次前 10 分钟；每 30 分钟 | 执行健康检查 | 场次阻塞，通知用户 |
| 开始前提醒 | 每场次开始前 10 分钟 | 检查任务是否已登记 | 未登记则催办读书员；5 分钟仍未登记则通知管理员 |
| 超时检查 | 每 5 分钟 | 检查执行中场次是否超过最长时长 | 转为超时待裁定，通知用户 |
| 漏跑记录 | 每场次结束后 | 标记未进入执行的场次 | 记录漏跑，不补跑 |
| 0 点催办 | 每日 00:00 | 催办未收尾、未回写的任务 | 仍未回写则进入异常通知 |
| 23:50 日报 | 每日 23:50 | 汇总场次、产出、异常、漏跑和登录失效次数，生成日报草稿 | 生成失败则通知管理员 |
| 导出与脱敏检查 | 日报确认后 | 生成公开产物，执行脱敏扫描 | 扫描不通过则阻断导出并通知 |
| 数据库备份 | 每日一次 | 备份数据库与审计日志 | 备份失败则通知用户 |
| 额度检查 | 每日一次 | 汇总 Gemini 额度使用情况 | 额度不足时按模型顺序回退并记录 |

### 9.2 异常通知触发条件

- 登录态失效；场次超时待裁定；资源冲突；漏跑；回写冲突超过 3 次；导出脱敏失败；备份失败；凭据异常。

### 9.3 通知渠道与送达确认

- **Cue 消息**：用于推送给用户的个人通知，是主渠道。
- **群消息**：只用于可见性较高的汇总通知，不承载任务推进。
- **送达确认**：以渠道回执为准；用户确认后记录确认时间。未确认的重要通知在 30 分钟后重发一次，仍未确认则升级为关键通知（仍只发在 Cue 消息）。

### 9.4 去重与静默

- 同一事件键（事件类型 + 对象 + 日期）在 24 小时内只发送一次。
- 02:00–06:00 为静默时段：期间事件只入队和记录，06:00 统一发送汇总。例外项见开放问题。

## 10. 书籍资产与数据分层

### 10.1 存放

- 原始 PDF 与 EPUB 存放在私有存储中，不进入公开仓库。理由：书籍版权与体积问题，且公开仓库不应承载私有资产。
- 系统只保存文件的引用、校验值（sha256）和大小。
- 公开仓库只保存系统导出的公开产物（摘要、笔记页面与链接）。

### 10.2 公开与私有分层

| 层级 | 内容 | 位置 | 访问 |
|---|---|---|---|
| 私有原始层 | PDF、EPUB、AI 原始回复、凭据引用 | 私有存储 | 仅管理员与用户 |
| 系统数据层 | 任务、场次、状态、审核、日志 | 数据库 | 按角色权限 |
| 公开产物层 | 允许公开的摘要、笔记页面、日报 | 导出到 GitHub，Pages 发布 | 公开 |

Pages 只从系统导出的公开产物生成，不直接读取私有层。

### 10.3 编号与目录

- 书目编号沿用“系列码 + 序号”，例如 `系列码-三位序号`，保持稳定且不因改名而变化。
- 目录仍按系列放在 `books/` 下，与既有约定一致。
- 公开标题用“AI读书”，机器键保持不变。

### 10.4 大文件策略（天涯全目录约 5.85GB）

- 按系列分批上传，每批完成后校验 sha256。
- 每份文件至少两份副本：本地私有存储与一份离线或冷存备份。
- 每季度做一次恢复演练，确认备份可用。
- 上传中断时从上次校验通过的批次继续，不重传全部。

## 11. 数据分析与文档沉淀

### 11.1 分析指标

- 阅读时长（按角色、书目、日期）。
- 产出数量（笔记、AI 问答、日报条目）。
- 完读率（按书目统计）。
- AI 问答覆盖率（已问答的章节占比）。
- 笔记链接数量与有效性。

### 11.2 文档沉淀

- 日报每天生成一条，存入 `daily-output/` 下的月度目录，例如按年月分文件夹。
- 月度产出目录汇总当月日报、笔记链接和指标。
- 知识库检索基于系统索引，只检索已合入的产出，未合入的草稿不进入检索结果。理由：避免未审核内容被误当作结论。

---

## 12. AI 链路落库

- **落库内容**：提示词、模型、调用时间、来源引用（书目、章节、页码）、原始回复引用、核验状态、核验结果。
- **原始回复单独存储并限权**，见第 13 节数据分层。
- **标签区分**：“亲读”（读书员实际阅读后的结论）、“AI问答”（模型回答）、“推断”（基于上下文的推测）。三者在界面和导出中都要分开显示。
- **金句默认“未逐字核验”**，只有完成逐字核验并记录核验人与方法后才改为“已核验”。理由：避免 AI 生成的文字被当作原文引用。
- **AI 输出不冒充亲读**，标签必须如实标注。
- **核验状态**：未核验、已核验、不通过。状态变更必须写入核验记录。

## 13. 外部集成

### 13.1 GitHub

- 系统为主，Git 为发布与审计归档。
- 系统导出的内容经脱敏检查后再提交。
- 读书员不再直接写入 GitHub。

### 13.2 微信读书

- 通过浏览器操作，登录态由用户手动维护（见第 8 节）。
- 书架上传需要登录，系统不得代为登录。

### 13.3 Gemini

- **模型顺序**：在系统配置中维护有序列表，额度用完时按顺序回退。
- **额度记账**：按模型、按日记录调用次数与额度消耗。
- **超时**：单次调用超时 150 秒。
- **失败回退**：超时或失败时尝试下一个模型，全部失败则任务进入阻塞并通知用户。
- **输出只作辅助**，需人工核对后才能成为产出。
- **密钥**：只以引用名保存在密钥存储中，系统库不存值。
- **调用记录**：每次调用写库，不含密钥。

### 13.4 Pages 发布

- 只从系统导出的公开产物生成。
- 发布前需通过脱敏检查。

## 14. 审核与合入

- 审核由管理员角色或用户完成。读书员不审核自己的产出。
- 系统记录审核人、时间、结论（通过、退回、有条件通过）和对象版本。
- 审核记录不可修改。若要更正结论，需新增一条审核记录或提交新版本。理由：保证审计可信。
- 管理员审核时可以抽查用户，用户也可以随时抽查管理员的审核。

## 15. 第三团队接入

- 新团队在系统中创建团队记录，选择角色模板（读书员、管理员），为每个 agent 颁发独立凭据。
- 新团队通过系统 API 领取任务、写回结果，不依赖旧群聊和 Git 的手工步骤。
- 接入前需完成检查清单：角色、凭据、资源、排班、通知渠道。
- 首次接入先试运行一本书，通过后才正式下发任务。

## 16. 迁移路径

### 16.1 导入对照

| 现有内容 | 导入目标 | 说明 |
|---|---|---|
| `book-registry.json` | 书目、资源、场次 | 活动锁转为资源记录，续读点保留 |
| `agent-roster.json` | Agent 与角色 | 只导入机器键与角色，不导入任何凭据 |
| 每日日志（`agent-communication/`） | 运行记录（只读历史） | 历史日志只读，不参与新状态 |
| memory | 记忆条目（带版本） | 保留审核门槛：记忆改动仍需审核 |
| todo | 任务 | 未完成项转为待下发任务 |

### 16.2 双写期

- 双写期为 2 周（建议值），期间 Git 与系统都记录，每日生成一份差异报告。
- 连续 10 个工作日差异为零或已全部解释后，才进入切换。

### 16.3 切换

- 切换窗口选在 02:00–06:00 禁读时段内，且当日无排班场次。理由：此时段无读书场次，切换不会影响运行中的任务。
- 切换后，系统为真相源；Git 只接收导出；读书员不再直接写 Git。

### 16.4 回滚

- 切换前打一个 Git 快照标签，作为回滚基准。
- 回滚时先冻结系统写入，把系统状态导出为与旧格式一致的 JSON，恢复读书员对 Git 的读取。
- 回滚时限为切换后 24 小时。超过后以系统为准，不再回滚。
- 回滚后做一次对账，确认无丢失的场次和产出。

## 17. 非功能要求

- **权限隔离**：每个角色只能访问自己的数据，越权请求拒绝并记录。
- **凭据不入库**：数据库、导出包、日志中都不出现凭据值。
- **审计日志**：所有写入、状态转换、审核与凭据操作都记录，只追加。
- **可回滚**：每个对象有版本号；可回到任一历史版本查看；切换有回滚方案（第 16.4 节）。
- **可导出 Git**：系统可导出与旧格式一致的 JSON 和 Markdown，导出前脱敏检查。
- **中文界面**：所有界面、通知、报表使用中文。
- **移动端可读通知**：通知内容简短，关键信息在首屏可见，不依赖网页才能理解。
- **脱敏扫描**：导出前检查 UID、群 ID、私人路径、凭据模式，不通过则阻断。

## 18. 阶段规划与验收

### 18.1 第一期：任务下发 + 登记 + 日报 + 通知

- **范围**：任务下发、读书员读取与登记、资源锁、回写、23:50 日报、0 点催办、通知（Cue 消息）、登录态检查。
- **验收标准**：
  - 连续 10 个工作日，所有排班场次都有登记记录或漏跑记录。
  - 任务从下发到完成的耗时，中位数不超过场次时长加 30 分钟（建议目标，待确认）。
  - 冲突写入被正确拒绝，无并发覆盖事件。
  - 登录失效时，场次停在登记前，并在 5 分钟内通知用户。
  - 日报每天准时生成。

### 18.2 第二期：数据分析

- **范围**：阅读时长、产出数量、完读率、AI 问答覆盖率、笔记链接统计、月度目录。
- **验收标准**：指标与人工统计的抽样误差在 5% 以内；月度目录每月自动生成。

### 18.3 第三期：AI 落库与知识库

- **范围**：AI 问答全量落库、核验记录、标签区分、知识库检索、Gemini 额度记账与回退。
- **验收标准**：所有 AI 调用都有记录；金句默认未核验；检索结果只包含已合入的产出。

### 18.4 量化指标（第一期验收用）

| 指标 | 定义 | 建议目标（待确认） |
|---|---|---|
| 任务耗时 | 从下发到完成的时间，中位数与 90 分位 | 中位数不超过场次时长加 30 分钟 |
| 漏跑率 | 漏跑场次数 / 排班场次数 | 不超过 5% |
| 登录失效次数 | 每周登录态失效次数 | 每周不超过 2 次，并呈下降趋势 |
| 人工介入次数 | 每周需要人工处理的事件数（不含审批） | 每周不超过 5 次 |

## 19. 开放问题

以下事项需要用户决定：

1. **系统托管位置**：云端服务还是沙箱内？建议：第一期放在沙箱内，便于快速验证；稳定后再评估迁移到云端。
2. **数据库选型**：建议第一期用单文件数据库起步，便于备份和导出；若并发增加再迁移到服务型数据库。
3. **用户界面形式**：网页看板，还是只靠通知？建议：第一期以通知为主，加一个只读的简易页面。
4. **预算与额度上限**：Gemini 每日额度、存储预算、通知数量上限分别是多少？
5. **哪些数据保留在 Git**：公开产物之外，是否允许其他数据进入 Git？
6. **谁能看数据**：除用户与管理员外，读书员能否看到其他角色的数据？建议：默认不能。
7. **通知渠道**：是否仅用 Cue 消息，群消息是否保留为汇总渠道？
8. **静默时段例外**：02:00–06:00 内，是否允许数据损坏或安全事件立即通知？
9. **是否自建后台**：继续用系统自带调度，还是接入现有工具？
10. **导出是否需要人工确认**：导出到 GitHub 前是否必须由用户点击确认？
11. **超时最长时长**：各槽位的宽限时间具体取多少？
12. **备份位置**：离线备份放在哪里，由谁保管？
